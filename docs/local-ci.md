# Local CI gate

Hosted GitHub Actions are optional and manual. The required gate is a full local run, bound to the exact Git tree, executed inside the project's `ci` lane of the `agent-resource` budget.

## Commands

| Command                                           | Purpose                                                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------- |
| `pnpm hooks:install-local`                        | Install the pre-commit and pre-push hooks for this worktree only.         |
| `python3 scripts/local-ci/install.py --uninstall` | Remove this worktree's hook path.                                         |
| `pnpm ci:local`                                   | The single required whole-suite pass, on the final head after the rebase. |
| `pnpm ci:verify`                                  | Validate the receipt for `HEAD` against the latest `origin/main`.         |
| `pnpm ci:merge --pr <n> [--execute]`              | Verify, apply the ticket policy, then squash merge (dry run default).     |
| `pnpm ci:land --pr <n>`                           | Rebase own PR if main moved, gate, squash merge: one `ci` ticket.         |

Rebase onto the latest origin/main first (single commit directly above it); each PR must then pass the full local CI (`pnpm ci:local` on that final head) before merge; if origin/main moves, rebase and rerun. `ci:verify` and `ci:merge` reject a head that is not a single commit directly above the latest `origin/main`, or whose receipt names another base.

Set `STATEACTION_LOCAL_FIXTURES=<env file>` for the bounded loopback PostgreSQL and S3 fixtures. Without it the fixture-backed stages fail; Docker is never started.

## Landing your own PR: `ci:land`

The owner of a ready PR (one commit, PR open, branch checked out and pushed) submits one ticket and moves on:

```
agent-resource run --lane ci --key land-<pr>-<head> -- pnpm ci:land --pr <n>
```

Inside that one `ci` ticket (no second ticket; nested gate and merge run under it) `scripts/local-ci/land.py`:

1. **Preflight, before any rebase, push or gate:** the PR is open, not a draft, targets `main`, its head repository is this repository and its author is `timothywangdev`; the head branch matches `wanghujie/sa-<n>-<slug>` and is the branch checked out (not detached) in this worktree, which `git worktree list` registers with it; the head equals local `HEAD` (and `--expected-head <sha>` when given); one non-merge commit above the base, clean tree, no rebase in progress; the fetch and push URL of `origin` are exactly `https://github.com/timothywangdev/stateaction[.git]` (fail closed: no SSH, lookalike host or other repository); both the default `gh` account and the push token belong to `timothywangdev`; the title/branch/declaration/one-PR-per-ticket policy of `ci:merge` (`github_policy.validate_pr`) passes. Failures: `foreign_branch`, `head_mismatch`, `not_single_commit`, `dirty_tree`, `identity`, `policy`, ... with nothing changed. Ownership limit: all agents share one GitHub account, so "own" means "an sa branch checked out in this worktree", not a per-agent identity; do not run `ci:land` on a branch you did not create.
2. If `origin/main` moved while the ticket waited, rebases the commit onto it. A conflict aborts the rebase and exits 7 `rebase_conflict`. If the rebase was conflict-free but changed the PR patch-id (new context), the earlier review no longer covers it: exit 6 `needs_review`, local branch restored, nothing pushed. A conflict-free rebase with an identical patch-id keeps the earlier review valid (`rebased: true` is reported). Otherwise it pushes with `--force-with-lease=<branch>:<exact old head>`; a push failure restores the local branch (exit 8). After a rebase that changed `local_ci.py`, `land.py`, `stages.json` or `github_policy.py`, the process re-executes itself so the code that gates is the rebased code (`runner_changed` if it cannot).
3. Runs the full gate (`run_pipeline`) on that exact head. A failure is never retried: the result names `failedStage` and `failedStageLog` (exit 1); fix, push and resubmit with a new key suffix (`-r2`, `-r3`; max 3 tickets per PR). Reusing the same key replays the old log.
4. On PASS takes the merge lock, re-fetches the PR (closed or merged meanwhile: exit 9 `pr_closed`), re-checks the base (if main moved after the gate it rebases and gates once more, `attempts` 2, else `base_moved`), then runs the existing `ci:merge` squash merge (`--match-head-commit`, receipt check, merged parent and tree check) and verifies MERGED. A failed `gh pr merge` is exit 5; a merge on an untested base is `fatal` exit 3.

Git network commands never carry the token in argv or on disk: it lives in an anonymous memfd (close-on-exec, so it dies with exec or SIGKILL) that only the `GIT_ASKPASS` script, which answers solely github.com's username/password prompts, reads. The script sits in a 0700 dir under `$XDG_RUNTIME_DIR` removed on every exit, before a re-exec and on SIGTERM (stale `land-auth-*` dirs older than 3 h are swept). `GIT_TRACE*` and `GIT_CURL_VERBOSE` are scrubbed from git's environment.

Every failure class writes a result file and returns a distinct exit code; only a gate failure is 1. Codes: 0 merged, 1 gate failed, 2 other refusal (read `reason`: `foreign_branch`, `foreign_origin`, `identity`, `head_mismatch`, `dirty_tree`, `base_moved`, ...), 3 fatal, 4 policy, 5 merge command failed, 6 `needs_review`, 7 `rebase_conflict`, 8 `push_failed`, 9 `pr_closed`, 10 unexpected error, 11 `merged_unverified`, 12 `interrupted` (SIGTERM/Ctrl-C), 75 other `Refused` (75 can also be a queue outcome: confirm with `agent-resource find`). Retrying: the same `--key` replays the old log, so after any non-zero code fix the cause and resubmit with a new key suffix (`...-r2`, `-r3`; convention: at most 3 tickets per PR, not enforced). Codes 3 and 11: stop and tell the owner. A re-execution after a runner change carries the attempt counter (at most 4 gate attempts in total). The structured result (`status`, `reason`, `exit`, `mergedSha`, `attempts`, `rebased`, `gate.wallSec`, `gate.stageSec`, `gate.failedStage`, `receipt`, `wallSec`) is printed as the LAST stdout line, so `agent-resource find --key <key>` shows it, and is written to `~/.cache/stateaction-local-ci/land/<key>.json` and `pr-<n>.json`. A resubmit of an already merged PR returns the stored result (a stored `fatal` stays exit 3); with no stored result it reports `merged_unverified` (exit 11) unless a PASS receipt exists for the merged tree. `scripts/local-ci/e2e_land.py` (`AGENT_RESOURCE_TEST=1`, manual) proves on a real lane: two queued tickets (the second starts stale, is rebased inside its ticket, gated and merged after the first), a policy refusal, a PR closed during the gate and a `needs_review` rebase.

## What a commit runs

The pre-commit hook runs the previous hook or `node scripts/platform/check-staged.mjs` only. It never starts `local_ci.py`; the whole suite is the explicit `pnpm ci:local` run.

## What the gate runs

`scripts/local-ci/stages.json` declares the stages. The runner:

1. refuses unless the process is inside the verified `agent-work.slice` / `agent-lane-ci-<project>.scope` cgroup (at most 6 GiB per job, 12 GiB aggregate, no swap); it re-executes itself under `agent-resource run --` when needed and refuses if the launcher is missing;
2. exports the head tree to a private temporary directory, so ignored files such as real `.env` credentials never take part, and installs dependencies against that export;
3. runs each stage serially, with the Nx/Gradle caches limited to deterministic stages (see Caching) and every integration/E2E/smoke stage uncached, with `NX_DAEMON=false`, Nx `--parallel=1`, Node `--test-concurrency<=2`, Flutter `--concurrency=2`, two-thread math libraries, a per-stage time limit and an output cap, with `docker`/`podman` shimmed to fail;
4. re-reads the tree after every stage, snapshots the exported tracked files and fails a stage that changed the tree, rewrote tracked source or left a process behind;
5. becomes a child subreaper, so detached (`setsid`) descendants re-parent to the runner. After every stage, and on failure, timeout or interruption (SIGINT/SIGTERM/SIGHUP), it terminates and reaps exactly its own descendants and fails the stage if their exit cannot be proved. After a successful Android tooling stage, a Gradle daemon gets up to five seconds to finish cache cleanup and exit on its own. Other service or emulator scopes are never touched;
6. before the first stage (so a dead fixture fails in seconds), probes the PostgreSQL and S3 fixtures and proves from `ss` and the kernel cgroup files that the loopback PostgreSQL and S3 listeners are served from `agent-service-postgres.scope` / `agent-service-storage.scope` inside the same 12 GiB, no-swap slice with a finite cap of at most 1 GiB. Otherwise the run fails with `agent-resource serve --name <postgres|storage>` instructions; the sanitized facts are recorded in the receipt.

No environment variable skips the hooks. A new full attempt first deletes any receipt for the same tree and records itself as the latest attempt, so a failed, cancelled or refused rerun can never leave an older PASS usable. The root `tests/test_*.py` unit suites run on the pinned CPU dependencies of `requirements-stera.txt` (Python 3.11 via `uv`); they need the `stera-sdk` submodule commit, which the runner exports from the checkout, `<git-dir>/modules`, or a directory named by `STATEACTION_LOCAL_CI_SUBMODULES`.

`pnpm ci:local` re-executes itself under `agent-resource run --lane ci --`: one FIFO ticket per project, no polling, no heavy-slot wait and no second pass. A ticket survives a killed submitter and its output is streamed to the caller; a queued run never deletes a receipt, only a run that actually starts supersedes the receipt of its tree. Other admission failures (no cgroup, no memory) still fail closed with exit 75. `ci:local` passes a deterministic ticket key (tree), so a rerun after a tool timeout attaches to the in-flight gate. `pnpm ci:merge --execute` also enters the `ci` lane (key: PR and tree; a dry run takes no ticket), takes the merge lock (a leaf lock after the ticket, bounded wait), re-checks the base just before merging and verifies the squash commit's parent and tree after merging; it needs a valid receipt for the exact head. The gate's Flutter/Gradle stages run under the same ticket (nested `android-build` requests are flattened); emulator tests are separate `emulator` submissions. See `docs/components/workstation-resource-guard.md`.

Every run, PASS, FAIL or INTERRUPTED, ends with a per-stage wall time table (stage, status, seconds, Nx cache hits/tasks) and the total; `run.json` keeps each stage's `durationSec`. Median seconds per stage, as a budget reference: `server-tooling` 40, `catalog-integration` 108, `jobs-controller-integration` 105, `runtime-smoke` 70, `server-auth-integration` 11, `local-ci-self-test` 35, `mobile-android-dart` 78, `mobile-backend-e2e` 110, `web-auth-e2e` 135.

Logs and `run.json` go to `~/.cache/stateaction-local-ci/logs/<run>/` (override with `STATEACTION_LOCAL_CI_HOME`). Fixture secrets are redacted from logs and never written to receipts.

## Jobs controller integration

The `jobs-controller-integration` stage runs `pnpm --filter @stateaction/jobs test:integration` (four real cases: happy path, controller loss, runner loss, and lost acknowledgement with an uncertain child) after the build, `python-sync` and `render-cli` stages. It uses the exported tree's checksum-pinned official Render CLI (`artifacts/platform-tools/render/render`) as a loopback `workflows dev` runner and the locked `workers/processing/.venv`, the production Next API, and a ledgered database and bucket on the bounded fixtures (no Docker, no cloud or provider calls). The processing pipeline is the local no-output fixture: this proves controller, executor and claim plumbing only, not hand-pose output, hosted or physical qualification. It never calls `apps/jobs/test-integration/run.sh`, which installs, rebuilds and rewrites tracked source. The stage is never cached, and the runner reaps every detached child it leaves. Each case tears down its own Next API, runner, controller and child when it ends: the whole stage ran in one guard scope capped at 256 tasks (threads included; a ci lane job now gets 512 because `web-auth-e2e` measured 256 of 256 and Chrome could not start threads), and keeping every case's processes alive until the end of the file exhausted that cap, so Node aborted with SIGABRT and no output when libuv could not start a worker thread (`clone3` EAGAIN). A controller process that dies now reports its exit code and signal instead of an empty `crashed` result.

## Caching

Speed comes only from existing mechanisms; no custom task cache exists.

- **Nx task cache.** Only the deterministic stages `server-tooling` and `mobile-android-dart` (build, typecheck, syntax, unit tests, format) may hit it. Every exported tree shares one private `NX_CACHE_DIRECTORY` (`~/.cache/stateaction-local-ci/nx-cache`), Nx Cloud stays off, and hits depend on Nx's input hashes: project sources, dependencies, lockfiles, `nx.json`/`package.json`/workflow inputs and the runtime commands listed in `sharedGlobals` (`node`, `pnpm`, `python3`, `uv`, `java`, `flutter` versions). A changed source, dependency, lockfile or toolchain therefore misses.
- **Never cached.** Every fixture-backed stage (catalog/storage integration, auth, Next HTTP E2E, mobile backend E2E, jobs controller integration, runtime and hosted smoke) and the Android capture spike build always run with `--skip-nx-cache` and fresh isolated fixtures. The runner appends the flag itself to any Nx stage that does not declare `"cache": "nx"`.
- **Dependency stores.** `pnpm install --frozen-lockfile --prefer-offline` hardlinks from the shared pnpm store, `uv`, pub and Gradle's `GRADLE_USER_HOME` caches are reused, and nothing is installed or downloaded twice. Gradle's task output cache is on only for `mobile-android-dart` (`-Dorg.gradle.caching=true`, same fixed export path). The first cold run showed a cached `testDebugUnitTest` skipping an undeclared fixture (`native-writer.mcap`) that the spike verifier reads, so `spikes/android/capture/app/build.gradle.kts` now declares `build/spike-fixtures` as a test-task output and a cache hit restores it. The configuration cache stays off and no daemon persists. The spike's `android-build` target runs once, uncached, as a dependency of `android-capture-spike-native:build`; stage deadlines are 10-30 minutes and Nx stages use `--nxBail`.
- **Export.** Each run gets a fresh export at a fixed path under the CI home, protected by a lock. A cache hit that rewrites a tracked source file still fails the stage.
- **Stage metrics.** Each stage also records informational `metrics`: CPU seconds (delta of the lane scope's `cpu.stat` `usage_usec`), sampled peak memory (`memory.current`, every 0.25 s) and the scope's cumulative `memory.peak`. Nx stages add `cache.taskTimings` (per task start offset, span to the next task line, cache hit; spans are upper bounds when Nx runs tasks in parallel). Metrics are never part of the tree binding or verification; receipts without them still verify. `pnpm ci:timing [--last N]` (read-only) prints per-stage median wall, CPU, cpu/wall, peak MiB over the last N PASS runs; runs recorded before the metrics show "not recorded". Metrics are informational and excluded from verification, so older receipts stay valid.
- **Receipt.** Each stage records `cacheMode`, `gradleBuildCache` and, for Nx, how many tasks were cache hits versus executed (with names); the receipt records `fresh`, the toolchain and its hash, and the total duration.
- **Forcing cold.** `python3 scripts/local-ci/local_ci.py run --tree HEAD --fresh` bypasses the Nx and Gradle caches. Compare its `totalDurationSec` with a following normal run for cold-versus-warm timing.

## Receipt

`~/.cache/stateaction-local-ci/receipts/<tree>.json` (outside Git, mode 0600) exists only after every stage passed on an unchanged tree. It records the tree and head, `origin/main` at test time, SHA-256 of the stage list and runner, each stage's command hash, status and log hash, toolchain versions, guard limits with the measured cgroup peak, fixture endpoints (no credentials) and the unautomated qualifications.

`ci:verify` / `ci:merge` accept a head only when: the receipt's tree equals the head tree; the stage list and runner in the head are the ones that ran; every declared stage passed with its declared command; the receipt is the latest attempt for the tree and was produced for this commit context (tree run on this head). Merge-time checks (exactly one non-merge commit directly above `origin/main`, `--match-head-commit`, merged-commit postcondition) are unchanged; the head contains the latest fetched `origin/main` as its direct parent and is exactly one non-merge commit. After a rebase the tree changes, so run `pnpm ci:local` again. `ci:merge` also requires the active `gh` account `timothywangdev`, the local `HEAD` to equal the PR head and the ticket policy, then calls `gh pr merge --squash --match-head-commit`. `main` is never pushed to.

## Not automated

Physical-device capture and company-profile operations, iOS hardware and hosted-provider (Render, R2) qualification are listed in every receipt under `unautomated`. They are never reported as passed.
