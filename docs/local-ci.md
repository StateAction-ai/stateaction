# Local CI gate

Hosted GitHub Actions are optional and manual. The required gate is a local run covering every task affected by the change, bound to the exact Git tree, executed inside the project's `ci` lane of the `agent-resource` budget.

## Commands

| Command                                           | Purpose                                                                        |
| ------------------------------------------------- | ------------------------------------------------------------------------------ |
| `pnpm hooks:install-local`                        | Install the pre-commit and pre-push hooks for this worktree only.              |
| `python3 scripts/local-ci/install.py --uninstall` | Remove this worktree's hook path.                                              |
| `pnpm ci:local`                                   | The single required pass (every affected task; fast docs checks if docs-only). |
| `pnpm ci:verify`                                  | Validate the receipt for `HEAD` against the latest `origin/main`.              |
| `pnpm ci:merge --pr <n> [--execute]`              | Verify, apply the ticket policy, then squash merge (dry run default).          |
| `pnpm ci:land --pr <n>`                           | Rebase own PR if main moved, gate, squash merge: one `ci` ticket.              |

Rebase onto the latest origin/main first (single commit directly above it); each PR must then pass the local CI with a fresh PASS receipt covering every affected task (`pnpm ci:local` on that final head; affected means `nx affected` from the head versus `origin/main`, and everything runs for the always-run paths below) before merge; if origin/main moves, rebase and rerun. A change whose every path is docs-only (`**/*.md` or `docs/**`, but never `AGENTS.md`, `docs/local-ci.md` or `scripts/local-ci/**`) needs a PASS receipt for the fast docs checks instead of the affected tasks; any other path runs the affected tasks. `ci:verify` and `ci:merge` reject a head that is not a single commit directly above the latest `origin/main`, or whose receipt names another base.

Set `STATEACTION_LOCAL_FIXTURES=<env file>` for the bounded loopback PostgreSQL and S3 fixtures. Without it the fixture-backed stages fail; Docker is never started.

## Landing your own PR: `ci:land`

The owner of a ready PR (one commit, PR open, branch checked out and pushed) submits one ticket and moves on:

```
agent-resource run --lane ci --key land-<pr>-<head> -- pnpm ci:land --pr <n>
```

Inside that one `ci` ticket (no second ticket; nested gate and merge run under it) `scripts/local-ci/land.py`:

1. **Preflight, before any rebase, push or gate:** the PR is open, not a draft, targets `main`, its head repository is this repository and its author is `timothywangdev`; the head branch matches `wanghujie/sa-<n>-<slug>` and is the branch checked out (not detached) in this worktree, which `git worktree list` registers with it; the head equals local `HEAD` (and `--expected-head <sha>` when given); one non-merge commit above the base, clean tree, no rebase in progress; the fetch and push URL of `origin` are exactly `https://github.com/timothywangdev/stateaction[.git]` (fail closed: no SSH, lookalike host or other repository); the tool resolves the `timothywangdev` credential itself (`GH_TOKEN` if it belongs to that account, else `gh auth token --user timothywangdev`, exported for every later `gh` call and the push) and refuses at once with `identity` and the fix (`gh auth login` as `timothywangdev`) when none works, so no `GH_TOKEN` export is needed; every pinned submodule (`stera-sdk`) must be available in some local checkout (this worktree, `<git-dir>/modules`, any `git worktree list` checkout, the repository's main checkout, or `STATEACTION_LOCAL_CI_SUBMODULES`), else `submodule` names `git submodule update --init stera-sdk` and the variable; the title/branch/declaration/one-PR-per-ticket policy of `ci:merge` (`github_policy.validate_pr`) passes: exactly one `Fixes SA-n` (`Refs` is rejected: a ticket is open or closed) and the acceptance-criteria checklist in the PR body is fully met (at least one `- [x] criterion: evidence` line, no `- [ ]` item), so an unmet criterion blocks the merge. Failures: `foreign_branch`, `head_mismatch`, `not_single_commit`, `dirty_tree`, `identity`, `policy`, ... with nothing changed. Ownership limit: all agents share one GitHub account, so "own" means "an sa branch checked out in this worktree", not a per-agent identity; do not run `ci:land` on a branch you did not create.
2. If `origin/main` moved while the ticket waited, rebases the commit onto it. A conflict aborts the rebase and exits 7 `rebase_conflict`. If the rebase was conflict-free but changed the PR patch-id (new context), the earlier review no longer covers it: exit 6 `needs_review`, local branch restored, nothing pushed. A conflict-free rebase with an identical patch-id keeps the earlier review valid (`rebased: true` is reported). Otherwise it pushes with `--force-with-lease=<branch>:<exact old head>`; a push failure restores the local branch (exit 8). After a rebase that changed `local_ci.py`, `land.py`, `stages.json` or `github_policy.py`, the process re-executes itself so the code that gates is the rebased code (`runner_changed` if it cannot).
3. Runs the full gate (`run_pipeline`) on that exact head. A failure is never retried: the result names `failedStage` and `failedStageLog` (exit 1); fix, push and resubmit with a new key suffix (`-r2`, `-r3`; max 3 tickets per PR). Reusing the same key replays the old log.
4. On PASS takes the merge lock, re-fetches the PR (closed or merged meanwhile: exit 9 `pr_closed`), re-checks the base (if main moved after the gate it rebases and gates once more, `attempts` 2, else `base_moved`), then runs the existing `ci:merge` squash merge (`--match-head-commit`, receipt check, merged parent and tree check) and verifies MERGED. A failed `gh pr merge` is exit 5; a merge on an untested base is `fatal` exit 3.

Git network commands never carry the token in argv or on disk: it lives in an anonymous memfd (close-on-exec, so it dies with exec or SIGKILL) that only the `GIT_ASKPASS` script, which answers solely github.com's username/password prompts, reads. The script sits in a 0700 dir under `$XDG_RUNTIME_DIR` removed on every exit, before a re-exec and on SIGTERM (stale `land-auth-*` dirs older than 3 h are swept). `GIT_TRACE*` and `GIT_CURL_VERBOSE` are scrubbed from git's environment.

Every failure class writes a result file and returns a distinct exit code; only a gate failure is 1. Codes: 0 merged, 1 gate failed, 2 other refusal (read `reason`: `foreign_branch`, `foreign_origin`, `identity`, `submodule`, `head_mismatch`, `dirty_tree`, `base_moved`, ...), 3 fatal, 4 policy, 5 merge command failed, 6 `needs_review`, 7 `rebase_conflict`, 8 `push_failed`, 9 `pr_closed`, 10 unexpected error, 11 `merged_unverified`, 12 `interrupted` (SIGTERM/Ctrl-C), 75 other `Refused` (75 can also be a queue outcome: confirm with `agent-resource find`). Retrying: the same `--key` replays the old log, so after any non-zero code fix the cause and resubmit with a new key suffix (`...-r2`, `-r3`; convention: at most 3 tickets per PR, not enforced). Codes 3 and 11: stop and tell the owner. A re-execution after a runner change carries the attempt counter (at most 4 gate attempts in total). The structured result (`status`, `reason`, `exit`, `mergedSha`, `attempts`, `rebased`, `gate.wallSec`, `gate.stageSec`, `gate.failedStage`, `receipt`, `wallSec`) is printed as the LAST stdout line, so `agent-resource find --key <key>` shows it, and is written to `~/.cache/stateaction-local-ci/land/<key>.json` and `pr-<n>.json`. A resubmit of an already merged PR returns the stored result (a stored `fatal` stays exit 3); with no stored result it reports `merged_unverified` (exit 11) unless a PASS receipt exists for the merged tree. `scripts/local-ci/e2e_land.py` (`AGENT_RESOURCE_TEST=1`, manual) proves on a real lane (including a fresh worktree with no `GH_TOKEN` and no `STATEACTION_LOCAL_CI_SUBMODULES`: identity and `stera-sdk` are found by the tool): two queued tickets (the second starts stale, is rebased inside its ticket, gated and merged after the first), a policy refusal, a PR closed during the gate and a `needs_review` rebase.

## What a commit runs

The pre-commit hook runs the previous hook or `node scripts/platform/check-staged.mjs` only. It never starts `local_ci.py`; the gate is the explicit `pnpm ci:local` run.

## What the gate runs

`scripts/local-ci/stages.json` declares four stages and the always-run list; the runner:

1. refuses unless the process is inside the verified `agent-work.slice` / `agent-lane-ci-<project>.scope` cgroup (at most 6 GiB per job, 12 GiB aggregate, no swap); it re-executes itself under `agent-resource run --` when needed and refuses if the launcher is missing;
2. exports the head tree to a private temporary directory, so ignored files such as real `.env` credentials never take part, and installs dependencies against that export;
3. runs each stage serially, with the Nx/Gradle caches limited to deterministic tasks (see Caching) and every integration/E2E/smoke task uncached, with `NX_DAEMON=false`, Nx `--parallel=1` (only the light `static` stage runs `--parallel=3`; `web:build`, every fixture target and the Flutter/Gradle stage stay serial), Node `--test-concurrency<=2`, Flutter `--concurrency=2`, two-thread math libraries, a per-stage time limit and an output cap, with `docker`/`podman` shimmed to fail;
4. re-reads the tree after every stage, snapshots the exported tracked files and fails a stage that changed the tree, rewrote tracked source or left a process behind;
5. becomes a child subreaper, so detached (`setsid`) descendants re-parent to the runner. After every stage, and on failure, timeout or interruption (SIGINT/SIGTERM/SIGHUP), it terminates and reaps exactly its own descendants and fails the stage if their exit cannot be proved. After a successful Android tooling stage, a Gradle daemon gets up to five seconds to finish cache cleanup and exit on its own. Other service or emulator scopes are never touched;
6. before the first stage (so a dead fixture fails in seconds), probes the PostgreSQL and S3 fixtures and proves from `ss` and the kernel cgroup files that the loopback PostgreSQL and S3 listeners are served from `agent-service-postgres.scope` / `agent-service-storage.scope` inside the same 12 GiB, no-swap slice with a finite cap of at most 1 GiB. Otherwise the run fails with `agent-resource serve --name <postgres|storage>` instructions; the sanitized facts are recorded in the receipt.

No environment variable skips the hooks. A new full attempt first deletes any receipt for the same tree and records itself as the latest attempt, so a failed, cancelled or refused rerun can never leave an older PASS usable. The root `tests/test_*.py` unit suites run on the pinned CPU dependencies of `requirements-stera.txt` (Python 3.11 via `uv`); they need the `stera-sdk` submodule commit, which the runner exports from the checkout, `<git-dir>/modules`, or a directory named by `STATEACTION_LOCAL_CI_SUBMODULES`.

### Four stages and the affected set

| Stage         | What it runs                                                                                                                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `setup`       | One script: toolchain record, `pnpm install --frozen-lockfile`, `uv sync --locked`, pinned Render CLI. It always runs (Nx itself comes from the install, so the affected set cannot be known first).    |
| `static`      | `nx affected -t build,typecheck,syntax,test,format,test-local-ci --exclude=tag:mobile-toolchain`. Nx-cached.                                                                                            |
| `mobile`      | `nx affected -t build,typecheck,syntax,test,format --exclude='*,!tag:mobile-toolchain'` (`nx affected` has no `--projects` option; the exclude form selects the tag). Nx-cached; Gradle build cache on. |
| `integration` | `nx affected -t catalog-integration,auth-integration,auth-e2e,integration,e2e` on the bounded fixtures. Every target is `cache: false`, `parallelism: false`.                                           |

The stage file holds targets and a tag selector per stage, never a project list. The runner builds each command and passes an explicit `--base=<merge-base of origin/main and HEAD> --head=<head commit>` (never `defaultBase`; the export has no history, so its private git repository reads the real repository's objects through an `objects/info/alternates` file, read-only). After `setup` it asks Nx for the project graph, `nx show projects --affected` and one `nx affected --explain` per stage; a stage whose selected set is empty is recorded `skipped` with the reason `skipped: unaffected` and never runs. `ci:verify`/`ci:merge` recompute the same plan in the checkout, which therefore must be a clean copy of the head with `node_modules` installed (`pnpm install --frozen-lockfile`). After the stage ran, every planned task must also appear in Nx's own output (`plan-mismatch` fails the stage).

Everything runs (`nx run-many`, the same targets, nothing skipped) when any changed path matches the `alwaysRunAll` list in `stages.json` (checked before any Nx result): `scripts/local-ci/**`, `stages.json`, `nx.json`, `pnpm-lock.yaml`, `uv.lock`, `workers/*/uv.lock`, the root `package.json`, `packages/server/migrations/**`, `AGENTS.md`, `docs/local-ci.md`, and the root files no Nx project owns (`.gitattributes`, `.gitmodules`, `.gitignore`, `.nxignore`, `.npmrc`, `.nvmrc`, `pnpm-workspace.yaml`, `requirements-inspection.txt`, `requirements-stera.txt`). It also runs everything, never narrower, when the repository is shallow, `origin/main` or the merge base cannot be resolved, or any Nx query fails; the receipt records which of these applied (`computation`: `ok`, `shallow`, `base-unresolved` or `failed`). A `packages/contracts/**` change reaches the mobile stage through the graph edge asserted by `test_nx_graph.py`.

Projection from the audit's stage medians, not yet measured on this gate: a `packages/server/src/**` change about 480-505 s in total, a `workers/processing/**` change about 160 s.

`pnpm ci:local` re-executes itself under `agent-resource run --lane ci --`: one FIFO ticket per project, no polling, no heavy-slot wait and no second pass. A ticket survives a killed submitter and its output is streamed to the caller; a queued run never deletes a receipt, only a run that actually starts supersedes the receipt of its tree. Other admission failures (no cgroup, no memory) still fail closed with exit 75. `ci:local` passes a deterministic ticket key (tree), so a rerun after a tool timeout attaches to the in-flight gate. `pnpm ci:merge --execute` also enters the `ci` lane (key: PR and tree; a dry run takes no ticket), takes the merge lock (a leaf lock after the ticket, bounded wait), re-checks the base just before merging and verifies the squash commit's parent and tree after merging; it needs a valid receipt for the exact head. The gate's Flutter/Gradle stages run under the same ticket (nested `android-build` requests are flattened); emulator tests are separate `emulator` submissions. See `docs/components/workstation-resource-guard.md`.

`ci:merge` and `ci:land` also pin the `gh` calls to `timothywangdev` the same way. Every run, PASS, FAIL or INTERRUPTED, ends with a per-stage wall time table (stage, status, seconds, Nx cache hits/tasks) and the total; `run.json` keeps each stage's `durationSec`. Skipped stages show status `skipped`. The `tooling:test-local-ci` task (in the `static` stage) runs `scripts/local-ci/run_self_tests.py`: one process per test class (per test for classes over 12 tests), three at a time, and it fails unless the number of tests that ran equals the number discovered. Medians recorded for the earlier fifteen-stage list are not comparable; read the new ones with `pnpm ci:timing`.

`run.json` (and the receipt) record `guard.counters.start` and `.end` for the run scope and the shared `agent-work.slice`: `pidsCurrent`, `pidsMax`, `pidsEventsMax` (thread/process spawns refused at the limit) and `memoryEvents`; `agent-resource status` prints the same live. After a run, `scripts/local-ci/flow_hook.py` runs `flowlog ci-run` (verdict, wall time, failing stage, per-stage times and cache hits, ticket from the `sa-<n>` branch, mode `ci:local` or `ci:land`) as a best-effort side channel: a missing, failing or slow `flowlog` (5 s limit, no credential in its environment) never changes the verdict; `FLOWLOG=off` disables it (the unit tests do). Read the flow with `flowlog report --project timothywangdev/stateaction`; phase events use `flowlog event` (`ticketlog` is a shim).

Logs and `run.json` go to `~/.cache/stateaction-local-ci/logs/<run>/` (override with `STATEACTION_LOCAL_CI_HOME`). Fixture secrets are redacted from logs and never written to receipts.

## Jobs controller integration

The `jobs:integration` task of the `integration` stage (`nx run jobs:integration`, which runs `pnpm --filter @stateaction/jobs test:integration` after the server and web builds) runs four real cases: happy path, controller loss, runner loss, and lost acknowledgement with an uncertain child. It needs the `setup` stage first. It uses the exported tree's checksum-pinned official Render CLI (`artifacts/platform-tools/render/render`) as a loopback `workflows dev` runner and the locked `workers/processing/.venv`, the production Next API, and a ledgered database and bucket on the bounded fixtures (no Docker, no cloud or provider calls). The processing pipeline is the local no-output fixture: this proves controller, executor and claim plumbing only, not hand-pose output, hosted or physical qualification. It never calls `apps/jobs/test-integration/run.sh`, which installs, rebuilds and rewrites tracked source. The stage is never cached, and the runner reaps every detached child it leaves. Each case tears down its own Next API, runner, controller and child when it ends: the whole stage ran in one guard scope capped at 256 tasks (threads included; a ci lane job now gets 512 because `web-auth-e2e` measured 256 of 256 and Chrome could not start threads), and keeping every case's processes alive until the end of the file exhausted that cap, so Node aborted with SIGABRT and no output when libuv could not start a worker thread (`clone3` EAGAIN). A controller process that dies now reports its exit code and signal instead of an empty `crashed` result.

## Caching

Speed comes only from existing mechanisms; no custom task cache exists.

- **Nx task cache.** Only the deterministic tasks of the `static` and `mobile` stages (build, typecheck, syntax, unit tests, format, runner self-test) may hit it. Every exported tree shares one private `NX_CACHE_DIRECTORY` (`~/.cache/stateaction-local-ci/nx-cache`), Nx Cloud stays off, and hits depend on Nx's input hashes: project sources, dependencies, lockfiles, `nx.json` and the toolchain named inputs (`jsToolchain`: node and pnpm versions; `pythonToolchain`: python3 and uv versions; `flutterToolchain`, used only by Flutter, Dart and Gradle tasks: java and flutter versions). Nx hashes resolved npm dependencies itself, so the root `package.json` and lockfile are inputs only of `tooling:format`; `pluginsConfig["@nx/js"].projectsAffectedByDependencyUpdates` is `auto`, so `nx show projects --affected` narrows a lockfile change to the projects whose resolved dependencies moved (measured: a `modal` bump selects `jobs`, `infra` and `tooling` only), but every `nx:run-commands` target still hashes all external dependencies, so task-level `nx affected` selects those targets after any lockfile change until each lists its own `externalDependencies`. `analyzeSourceFiles` stays off: turning it on adds static import edges (for example `contracts` to `server` from a test import) that would make every change reach every project. A changed source, dependency, lockfile or toolchain therefore misses.
- **Never cached.** Every task of the `integration` stage (catalog/storage integration, auth, Next HTTP E2E, mobile backend E2E, jobs controller integration, runtime and hosted smoke) always run on fresh isolated fixtures. Each of their Nx targets (`server:catalog-integration`, `server:auth-integration`, `web:auth-e2e`, `mobile-backend-e2e:e2e`, `jobs:integration`, `infra:integration`) declares `cache: false` and `parallelism: false` on its project, so only the target itself reruns while its `build` dependencies may hit the cache; the runner fails the `integration` stage when any task selected for it was replayed from cache or missing from the Nx output (`cached-fixture`), and `--fresh` still adds `--skip-nx-cache`. A per-run or per-worker database cloned from a verified, content-keyed, sealed template is a fresh fixture (user-approved 2026-11-22).
- **Template databases.** Catalog, Next E2E, jobs and mobile-backend databases are cloned with `CREATE DATABASE ... TEMPLATE` from a migrated template instead of re-applying the migrations per database (`scripts/platform/db-template.mjs`). The template is named `sa_tpl_<kind>_<key16>`; the key is the hash of `packages/server/migrations/**` plus `packages/server/src/migrations.ts` (the role and grant setup), and for the large-catalog test additionally of its seed code (`plans-seed.ts`, the harness and the catalog, jobs, datasets and admission sources). The first run on a new key builds it once under a cluster-wide advisory lock into a staging database, fingerprints it (schema, indexes, migration checksums, exact row counts), stores key and fingerprint in the database comment, seals it (`IS_TEMPLATE`, `ALLOW_CONNECTIONS false`) and only then renames it, so nobody can connect to or write to a sealed template. Every clone replays the template's database-level ACL (cloning does not copy it) and is re-fingerprinted before it is handed out; a mismatch drops the clone and the template and rebuilds once, a second mismatch fails the run. A changed migration or seed file means a different name, so the old template is simply no longer used. Templates hold no test-written data, secrets or recordings. Clones are ordinary ledgered run databases (`sa_cat_<run>_<hex>`, owner `migration_owner`) and are reaped like any other, after normal and killed runs. Templates are shared across runs and never reaped by a run; the run ledger records a non-reapable `template` event with the key. Retention: `node scripts/platform/local-fixtures.mjs templates prune` drops comment-proven `sa_tpl_*` templates older than 24 hours, except names passed with `--keep`. `freshDatabase({ migrate: false })` still creates an empty database for the migrator tests.
- **Dependency stores.** `pnpm install --frozen-lockfile --prefer-offline` hardlinks from the shared pnpm store, `uv`, pub and Gradle's `GRADLE_USER_HOME` caches are reused, and nothing is installed or downloaded twice. Gradle's task output cache is on only for `mobile` (`-Dorg.gradle.caching=true`, same fixed export path). The first cold run showed a cached `testDebugUnitTest` skipping an undeclared fixture (`native-writer.mcap`) that the spike verifier reads, so `spikes/android/capture/app/build.gradle.kts` now declares `build/spike-fixtures` as a test-task output and a cache hit restores it. The configuration cache stays off and no daemon persists. The three mobile build targets (`mobile:build`, `android-capture-spike:build`, `android-upload-spike-native:build`) are Nx-cached verification tasks keyed on their sources, the pinned toolchain and the installed Android SDK package revisions (`androidToolchain` runtime input); `pub get` runs inline in the executing target (`scripts/mobile/run.py`), never as a separate always-run task, so a cache hit runs no Flutter or Gradle at all. No Gradle dependency lockfile exists: every direct version is exact and `test_nx_graph.py` rejects a dynamic one; stage deadlines are 10-30 minutes and Nx stages use `--nxBail`.
- **Export.** Each run gets a fresh export at a fixed path under the CI home, protected by a lock. A cache hit that rewrites a tracked source file still fails the stage.
- **Stage metrics.** Each stage also records informational `metrics`: CPU seconds (delta of the lane scope's `cpu.stat` `usage_usec`), sampled peak memory (`memory.current`, every 0.25 s) and the scope's cumulative `memory.peak`. Nx stages add `cache.taskTimings` (per task start offset, span to the next task line, cache hit; spans are upper bounds when Nx runs tasks in parallel). Metrics are never part of the tree binding or verification; receipts without them still verify. `pnpm ci:timing [--last N]` (read-only) prints per-stage median wall, CPU, cpu/wall, peak MiB over the last N PASS runs; runs recorded before the metrics show "not recorded". Metrics are informational and excluded from verification, so older receipts stay valid.
- **Receipt.** Each stage records `cacheMode`, `gradleBuildCache` and, for Nx, how many tasks were cache hits versus executed (with names); the receipt records `fresh`, the toolchain and its hash, and the total duration.
- **Forcing cold.** `python3 scripts/local-ci/local_ci.py run --tree HEAD --fresh` bypasses the Nx and Gradle caches. Compare its `totalDurationSec` with a following normal run for cold-versus-warm timing.

## Docs-only changes

`scripts/local-ci/stages.json` holds the rule (`docsOnly`: `docsPaths`, `forceFullPaths`, the setup stages and the checks) in one place. The runner lists `git diff --raw -M <merge-base with origin/main> <head>` (`--name-status` plus modes; submodule-ignore and diff-driver settings are overridden, and any symlink or submodule entry runs the full suite) and the diff is docs-only only when every path on both sides of every change (renames and deletions included) matches `**/*.md` or `docs/**` and none is `AGENTS.md`, `docs/local-ci.md` or under `scripts/local-ci/**`. A shallow clone, an unresolvable base, a failed or empty diff, an unusual path name or a missing rule runs the full suite (the log says why); `local_ci.py run --full` forces it.

A docs-only run executes the `setup` stage, then `docs-checks` (`nx run tooling:docs-check`: `prettier --check` and a relative link and anchor check of the changed docs, cached by Nx on the docs tree, the changed-path list and the tracked file list; the changed docs are checked, and a deleted or renamed doc is also checked for inbound links from every other Markdown file; a renamed heading is not caught) and `docs-affected` (`nx affected -t build,typecheck,syntax,test,format --files=<changed paths>`, which runs the tasks Nx selects for those files, that is the ones that name a changed doc as an input, such as `infra:format` and `infra:test` for `docs/components/render-deployment.md`). Before `docs-affected`, `nx affected -t <guardedTargets> --graph` asks which skipped targets (`guardedTargets`: the fixture, e2e and `test-local-ci` tasks) the changed files would select; if any, the run drops the docs-only attempt and runs the full suite (the six fixture targets exclude Markdown from their inputs, so an ordinary doc selects none). The receipt has `mode: docs-only`, `docsOnly` (rule version and SHA-256, merge base, changed entries and paths, affected projects, checks) and every other stage as `skipped: unaffected` with the changed paths and affected projects as evidence. `ci:verify` and `ci:merge` recompute the classification and the affected set from the head and reject the receipt when its changed-path list, rule hash or skipped list differ, when the diff touches a non-docs path, when the recomputed (project-level) affected set differs, when the changed docs select a skipped (guarded) task, when the set cannot be recomputed, or when the head is not directly above the latest `origin/main`. The receipt stays bound to the exact tree, so a later code change needs a new run. Hosted `checks.yml` stays manual and keeps the full suite.

## Receipt

`~/.cache/stateaction-local-ci/receipts/<tree>.json` (outside Git, mode 0600) exists only after every stage passed on an unchanged tree. It records the tree and head, `origin/main` at test time, the affected set (below), SHA-256 of the stage list and runner, each stage's command hash, status and log hash, toolchain versions, guard limits with the measured cgroup peak, fixture endpoints (no credentials) and the unautomated qualifications.

`ci:verify` / `ci:merge` accept a head only when: the receipt's tree equals the head tree; the stage list and runner in the head are the ones that ran; every declared stage passed with its declared command or is recorded `skipped: unaffected` with the affected set that justifies it; the receipt is the latest attempt for the tree and was produced for this commit context (tree run on this head). Merge-time checks (exactly one non-merge commit directly above `origin/main`, `--match-head-commit`, merged-commit postcondition) are unchanged; the head contains the latest fetched `origin/main` as its direct parent and is exactly one non-merge commit. After a rebase the tree changes, so run `pnpm ci:local` again. `ci:merge` also requires the active `gh` account `timothywangdev`, the local `HEAD` to equal the PR head and the ticket policy, then calls `gh pr merge --squash --match-head-commit`. `main` is never pushed to.

### Affected set in the receipt

`affected` holds the base SHA (the head's direct parent and the latest `origin/main`), the head commit, `computation`, `runAll`, the matched always-run paths (empty when none), the changed-file count and hash, the affected project set, per stage the selected tasks and the skipped tasks with the reason `skipped: unaffected`, and an `evidenceSha256` over all of it (an unkeyed consistency hash: recomputation, not the hash, resists tampering). `ci:verify` and `ci:merge` recompute the changed files and the always-run match with git, and, for a narrowed receipt, the project set and every stage's selection with Nx; they reject the receipt when the base is not the latest `origin/main`, when the recomputed set differs (a tampered set, or a skipped task the recomputed set selects), when a stage is skipped for any other reason, when the set was narrowed despite a matched path or a failed computation, when a fixture task lacks proof it executed uncached, or when the set cannot be reproduced at all (fail closed). A receipt without the `affected` block does not verify.

## Not automated

Physical-device capture and company-profile operations, iOS hardware and hosted-provider (Render, R2) qualification are listed in every receipt under `unautomated`. They are never reported as passed.
