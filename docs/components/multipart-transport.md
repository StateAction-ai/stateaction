# Multipart transport (SA-20, SA-21)

Status, 2026-11-02: **control plane implemented and bound to Next routes on top of merged SA-19 (`cb5edee`, migration 004).** Tested against real Postgres (restricted role), real SeaweedFS and the production `next start` build with real Better Auth sessions. Real R2 behaviour is not qualified by this ticket's workers; the root runs the scoped R2 probe. The worker output contracts are **published in `catalog.v5`** (`http.output-create.v1`, `http.output-plan.v1`) on top of merged SA-16 `catalog.v4`.

All media moves directly between the client and private object storage through short-lived presigned `UploadPart` PUTs. The API only handles bounded JSON control bodies.

## Guarantees

1. **Reserve before provider.** `reserveSourceFile` (SA-13) or the output reservation inserts the `files` row with the server-chosen key `recordings/<rec>/sources/<file>/e<epoch>/<role>` or `jobs/<job>/outputs/<file>/e<epoch>/<slot>` before any provider call. Clients never send keys, buckets, owners, job IDs, ranges or part sizes.
2. **Provider ID persisted before URLs.** Creation runs outside any DB transaction behind a leased claim. The upload ID is written to `files` (write-once per epoch, enforced by a trigger) before `signParts` will issue anything. An uncertain earlier creation (lost response, DB failure after provider success) is reconciled by listing the exact key and adopting the single upload. It is never blindly repeated. Several uploads for one key are `provider_ambiguous` and block progress.
3. **Server-validated plan.** Part numbers (integers, unique, within the frozen plan, at most 32), offsets, lengths, count and byte caps, role and `expectedTransportEpoch` are checked on every request. Each presigned URL binds the exact part length (`content-length` is a signed header; a longer body is refused by the provider). Small manifests and worker outputs also use multipart (one part).
4. **Receipts are exact, durable, idempotent and corroborated.** `{partNumber, etag, sizeBytes}` is checked against the planned length, then confirmed against the provider's `ListParts` before it is journaled in `file_part_receipts`, so a client cannot invent receipts. An identical replay is a no-op. A different ETag for a journaled part is accepted only when the provider confirms it (a re-uploaded part); otherwise it conflicts. The database independently rejects receipts outside the plan or epoch.
5. **No revived authority.** Owner calls need an unexpired session row of that user, an enabled `collector` role, an owned, non-deleted recording and the recording's registered collection permission still active (`ingest_permission_ok`, so revoking the evidence stops uploads at once). Job calls need a `running` job inside its deadline, and the file's own `job_id`. Humans cannot reach output files and workers cannot reach source files. A stale epoch is `409`. A restart (SA-21) starts a new epoch with no receipts.
6. **Worker outputs.** Idempotent per server-validated `slot` (a safe relative path unique within the job). Each file is limited to 32 GiB and each job to 64 GiB. Allocation enforces the immutable file count in `job_inputs.max_output_files`, which defaults to 512 and is configurable at admission up to 2,000. The route layer calls `authenticateService({ kinds: ["worker"], scope: "job:output", jobId })` against `JobCapabilityStore`. The bearer's SHA-256 must equal `jobs.capability_token_sha256` of a `running` job inside its `execution_deadline` for audience `stateaction-api`. The controller issues the capability with the `job:output` scope.
7. **JSON only.** `readBoundedJson` requires `application/json`, rejects a declared length over 16 KiB, and cuts an undeclared stream off at the bound without buffering it. Responses carry `cache-control: no-store` because they hold bearer URLs. URLs are never logged or persisted.

## Not claimed

- **ETags and the R2 multipart ETag are provider receipts**, not the whole-file SHA-256. The declared `sha256` is stored immutably and verified later at full EOF by a separate reader (`MultipartProvider.readObject` is the stream seam). Nothing here marks a file `verified`.
- SeaweedFS lists a re-uploaded part number more than once, so a receipt is corroborated by any exactly matching entry. S3 and R2 list one entry per part. Qualify R2 behaviour separately.
- `http.upload-plan.v1` enumerates source roles. Worker outputs use the closed `http.output-create.v1` request (`{slot, role, sizeBytes, sha256}`, 4 KiB cap) and `http.output-plan.v1` response (`outputFileRole`, 16 KiB cap, same `upload_plan` part-count rule), added by `catalog.v5` (`/internal/v1`). The path and credential identify the job. The Next handlers parse the output request and validate each response against the owner or worker plan contract. The server enforces the byte and admitted file limits above and returns `409` when the same slot is used with different content.
- Remaining outside this ticket: real R2 qualification (root probe), hosted CI and the Render deployment of the routes. No new environment variables or services are needed.

## Completion and recovery (SA-21)

Four POST transitions on the frozen `http.upload-transition.v1` body (`{expectedTransportEpoch}` only; clients never send part lists or keys). Every one answers with the file's current plan (`http.upload-plan.v1` for owners, `http.output-plan.v1` for jobs). Owner routes are `/api/v1/uploads/{fileId}/{reconcile,complete,cancel,restart}`; worker routes are `/internal/v1/jobs/{jobId}/outputs/{fileId}/{…}` with the same `job:output` capability. A stale epoch is `409`. **No migration and no contract change** were needed: restart reuses the `files` epoch/key/upload columns SA-13 already guards, and the per-file claim table of migration 005.

Provider truth comes only from authoritative reads of the exact, never-reused key: `HEAD`, the fully paginated multipart-upload listing, and paginated `ListParts` of the persisted upload. The journal is evidence, not truth.

| Transition  | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `complete`  | Lists every part `1..partCount` (pages of 1,000, so plans of up to 10,000 parts), requires each to exist with exactly the planned length and no conflicting duplicate, heals journal rows the provider confirms (lost DB write), then durably moves the file to `completing` **before** asking the provider to complete with the server-built ordered list. Success is proven by `HEAD` (size must equal the declared size), not by the reply. Source files finalize through SA-19 `recordSourceCompletion` (file completed and admission eligibility in one transaction); outputs through a guarded update. Missing/short parts return `409` naming them; nothing is completed. Only an explicitly named refusal (`InvalidPart`, `InvalidPartOrder`, `EntityTooSmall`) reopens the same epoch; a timeout, 5xx, 403/404 or lost reply leaves `completing`.                                      |
| `reconcile` | `reserved`: re-runs initialization for the exact key (adopt the single listed upload or create; several uploads are `provider_ambiguous` and block). `uploading`: heals lost receipts from the provider listing. `completing`: only `HEAD` of the exact key can settle it (object present with the declared size → finalized). Otherwise it stays visibly unknown (`409`): elapsed time, an alive or vanished upload or a 403/404 never prove an earlier completion call has stopped, so it is never repeated, aborted or restarted. The journal is frozen once `completing` begins (the database refuses receipt changes outside `uploading`), which is the durable record of the exact part set sent.                                                                                                                                                                                         |
| `cancel`    | Allowed only from `reserved`/`uploading`; the database transition is the arbiter against a racing completion (once `completing`, cancel is refused). Provider cleanup then aborts every upload listed at the exact key plus the persisted ID; a replay repeats the cleanup, and anything left is bounded by the seven-day lifecycle. A source file of a sealed recording cannot be retired (SA-13 `SAC04`): restart it instead.                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `restart`   | Only for a **proven retired, unfinished** `uploading` transport (never `completing`): no object at the key, nothing listed after the seven-day window (anything still listed at the exact key is then aborted, whatever its ID), or, before the window, no listed upload **and** `ListParts` of the persisted ID reports it gone. Advances `transport_epoch` by one with a new key and upload, in the same logical file (identity, size, SHA-256, owner/job unchanged). Receipts belong to the old epoch and are never read again, so **the whole object must be sent again** (the new epoch starts with zero receipts). If an object already exists at the old key the file is finalized instead; `completed`/`verified` files are never reopened. If provider initialization is down after the epoch advance the plan is returned as `reserved` at the new epoch and `reconcile` finishes it. |

R2 create-time and list-time upload IDs can differ for one upload. No path here infers a distinct or orphaned upload from ID inequality: decisions use the exact-key listing as a whole, HEAD and ListParts with the persisted ID. Provider-side serialization uses the existing per-file claim lease (default 300 s for transitions), shared with initialization.

Not claimed by SA-21: ETags and lengths do not prove content, so nothing here marks a file `verified`; the full-EOF SHA-256 reader is a later ticket (the `readObject` provider seam exists for it). Old-epoch receipt rows remain as inert history (the application role has no `DELETE` on them). Real R2 behaviour of the new provider calls (`CompleteMultipartUpload`, `HEAD`, `ListParts` after abort) is qualified by the root with a tiny fixture.

## Migration

`005` is the only transport migration (SA-21 added none); it follows the published `004` and is applied by the real migrator; `001`-`004` are byte-identical to main (hash-pinned in `migrations.test.ts`). `grantAppRole` calls `stateaction_grant_transport` when present, so the restricted role gets exactly: `SELECT, INSERT` on receipts and output slots, `UPDATE (etag, corroborated_at, updated_at)` on receipts, and full access to the claim table. It gets no `DELETE` on receipts or slots; `transport-grants.test.ts` asserts the matrix and idempotent re-granting.

## Tests

`pnpm --filter @stateaction/server test` covers plan arithmetic and the bounded reader with no services. `pnpm exec nx run server:integration` (uncached) starts a throwaway Postgres and a real SeaweedFS on ephemeral loopback ports and runs the transport suites with the catalog suites: direct presigned PUTs, signed-length enforcement, receipts, completion of the journaled object, provider outage/lost response/ambiguity/DB failure, concurrent initializers and receipt writers, revoked sessions and roles, stale epochs, output caps and database-level guards.

The Next layer is covered by `test/transport-next.test.ts` (authority resolution, fail-closed configuration) and `apps/web/test-e2e/uploads.e2e.test.mjs` (`nx run web:auth-e2e`, uncached): owner, other-collector, wrong-role, pending, disabled, expired and deleted sessions, revoked role and permission, worker capability (other job, expired deadline, finished job, cookies), malformed/oversized/truncated bodies, duplicate and racing requests, and a paused provider.

SA-21 adds `test/transport-provider.test.ts` (page walk of 2,500 parts, `NoSuchUpload`/`NotFound` mapping, no I/O) and `test-integration/transport-recovery.test.ts` (real Postgres with the restricted role, real SeaweedFS): lost complete reply, provider success then database failure, completion-in-flight races, stale epochs, cancellation, seven-day restart (new epoch/key, no old receipts, stale requests fail), provider-lost upload before expiry, existing-object-never-restarts, ambiguous multiple uploads, lost create reconciliation, and a 1,537-part plan (scripted provider over real Postgres, since 1,537 real 64 MiB parts are impractical) including create/list alias IDs.

`apps/web/test-e2e/uploads-recovery.e2e.test.mjs` is the SA-21 HTTP-path proof for the eight new routes on the production `next start` build (owner session and `job:output` capability, live role/permission/session/deadline revocation, stale epochs, bounded closed JSON, complete/reconcile/cancel/restart including provider loss and full retransmission at epoch 2, published `http.upload-plan.v1`/`http.output-plan.v1` checks). It runs on the shared fixture adapters (Docker, or the bounded ledger-owned local fixtures under `STATEACTION_LOCAL_FIXTURES`, where each run owns and reaps its own database and bucket; Next connects only as `stateaction_app`). The provider-outage cases drive a loopback proxy (`outage-proxy.mjs`) in front of the store, so they run on every fixture mode without a Docker pause.
