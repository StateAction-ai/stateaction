# Android native background upload (SA-57)

StateAction.ai · 2026-11-02 · **Implemented behind a build gate, not enabled, not physically qualified.** This document describes the code in `packages/stera_recorder/android/src/main/kotlin/open/fpvlabs/stera/upload/` and its Dart bridge. It replaces the old "Android uploads are unsupported" guard only once SA-22 wires the owner-bound orchestrator and the gate is flipped by a reviewed build. Public Start does not enable it.

## Scope and authorities

| Concern                                                                                                                                  | Owner                                                                                                                                 |
| ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Create, reserve, epoch, completion list, provider complete, restart, cancel                                                              | **API only** (`/api/v1/uploads/...`, SA-19/20/21). Native never calls create, cancel or restart and never holds provider credentials. |
| Which sources to upload, when, restart after `needs_orchestrator`                                                                        | SA-22 owner-bound orchestrator (Dart)                                                                                                 |
| Move bytes under the OS scheduler, renew URLs, report receipts, reconcile, request completion, survive Dart suspension and process death | **This module (native)**                                                                                                              |

Native calls exactly: `GET /api/v1/me`, `GET /api/v1/uploads/{id}`, `POST .../parts/sign`, `PUT .../parts/receipts`, `POST .../reconcile`, `POST .../complete`, with the frozen `http.*.v1` bodies (`expectedTransportEpoch` only; no completion lists, keys or part sizes). No new HTTP DTO or catalog entry was invented. The MethodChannel is an app-internal typed control (`schemaVersion` 1), not an HTTP contract.

## Scheduling by API level (primary sources, read 2026-11-02)

| API  | Mechanism                                                                                                           | Notes                                                                                                                                                                                                                                                                                                                          |
| ---- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 34+  | `JobScheduler` user-initiated data-transfer (UIDT) job, `UploadJobService`                                          | Needs `RUN_USER_INITIATED_JOBS`, a notification posted with `setNotification`, `setUserInitiated(true)`, network/charging constraints, `setEstimatedNetworkBytes`. Scheduled **only from a visible user action**; the bridge refuses `resume` otherwise (`not_visible`).                                                       |
| 33   | Unique WorkManager `Worker` with `setForegroundAsync` (`dataSync` foreground service), enqueued `APPEND_OR_REPLACE` | Constraints from the same policy. A new request never cancels a still-running worker; it runs after it. A run that finds the single run lock held while work remains returns `retry` instead of `success`, so the queue cannot be stranded. API 33 is the floor because the SA-18 source identity needs nanosecond file times. |
| < 33 | Unsupported (`capabilities().scheduler == unsupported`)                                                             | The identity is refused rather than weakened to whole-second times.                                                                                                                                                                                                                                                            |

Honest limits (no unlimited-background promise):

- A UIDT job must be scheduled while the app is visible (or in an allowed condition); otherwise `schedule()` fails. The whole `JobInfo` construction **and** `schedule()` run inside the same guard, so a builder failure also becomes a durable needs-visible-Resume. Visibility is the union of lifecycle callbacks and a live window probe seeded when the plugin attaches or re-attaches to an activity that had already started. We then record **needs-visible-Resume** durably and post a "Upload paused - tap to resume" notification; we never retry illegally or silently report "unsupported".
- UIDT is not subject to standby-bucket quotas but the system stops it for a lost developer constraint, thermal state, health or low memory (`onStopJob`, retried by the OS). The user's Task Manager **Stop kills the process without `onStopJob`** and prevents rescheduling: the journal is the recovery source and the next visible Resume continues. Only constraints the UIDT API allows are used (network, charging, persisted, backoff, estimated bytes).
- A `dataSync` foreground service may run **6 hours per 24 hours** in the background (Android 15+, resets when the user brings the app to the foreground); `onStopped` stops effects and the journal resumes later. A WorkManager worker started by constraints from the background cannot legally start a foreground service: it records needs-visible-Resume instead.
- A persisted UIDT job may be re-run by the OS after reboot; whether and when it does is a **physical-device gate**, not claimed here.

Sources: [UIDT](https://developer.android.com/develop/background-work/background-tasks/uidt) (updated 2026-10-28), [foreground service background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [foreground service types (`dataSync`)](https://developer.android.com/develop/background-work/services/fgs/service-types), [foreground service timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout), [WorkManager long-running workers](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running).

## Transfer invariants

- One source at a time (a process-wide run lock); the API issues 64 MiB parts; **at most 2 provider PUTs** in flight; **at most 3 temporary chunk files** (a semaphore; steady state is 2 because each PUT thread holds one). Copy/PUT buffer is 128 KiB; the whole file or part is never held in memory.
- The source is opened read-only through the SA-18 confined-descriptor rules (`O_NOFOLLOW`, kernel path equals `root/rel`, `lstat` names the same inode) and compared to the frozen sealed identity (dev, inode, size, ns mtime/ctime). Reads are positional (`pread`), identity is re-proved every 16 MiB and after the last byte. A source that grew, shrank, was replaced or escaped its root becomes `source_blocked`; the source is never edited, deleted or adopted.
- Journal (`no_backup/native_upload/journal.v1.json`, atomic temp + fsync + rename + directory fsync) keyed by owner + backend + recording + file + transport epoch. Stores part state, ETag, size, attempts, next-attempt time and hard expiry. It never stores signed URLs, cookies or tokens; a corrupt or undecodable journal (including an unknown part state or malformed number) fails closed, is preserved byte for byte and is never overwritten. A failed durable write (e.g. the directory fsync after the rename) invalidates the in-memory cache, so the next access re-reads the real disk state instead of computing from a stale record.
- Owner gate (`gate.v1.json`): bound owner, origin, **generation**, policy and capture pause. Every control call, PUT start and chunk re-reads it; an older generation stops the run. Logout or account switch bumps the generation, cancels the active run, wipes the native session and marks unfinished work `blocked_owner` under its own owner (kept, not adopted, not deleted). Same-owner re-bind plus a visible Resume re-arms it. A failed or uncertain cancel leaves parts `uploading`, which forces reconcile before any repeat.
- Policy (unmetered network, charging, capture pause) is persisted and enforced both as OS job constraints and again inside the engine before each effect. Capture pause cancels the active run and the job.
- Retry: capped exponential backoff 5 s to 5 min with 25% jitter, 8 attempts per part, 8 control attempts, 4 URL renewals per part per run, and a hard task lifetime of 6 days bounded by the plan's `transportExpiresAt`. Exhaustion becomes `needs_visible_resume`; expiry becomes `needs_orchestrator`.
  - A part attempt is consumed **durably before** the PUT starts (a process death mid-PUT cannot loop for free); a deliberate cancel (pause, policy, owner change, system stop) refunds it, a process death does not. A PUT interrupted by process death is reconciled and then backs off before the repeat.
  - Every `backoff` reason persists its retry time (`retryAtMs`); a wake before it (including a fresh process) performs no request. Server `completing` waits use their own persisted counter (`completingAttempts`), never reset by a successful control call, grow exponentially and end in `needs_orchestrator: completing_unresolved` after 8.
  - A control outage (receipts or sign) opens one persisted backoff window: no new PUT starts and no request is made until it elapses, then landed-but-unreported receipts are flushed. Failures inside an open window are the same outage and are not counted per part.

## Protocol rules

1. Start of every run (wake): verify `GET /api/v1/me` returns the frozen owner's Better Auth id **and** an active collector. A caller-supplied owner id is never server identity. Mismatch is `blocked_owner`. `status` returns tasks only for the currently bound owner; any other supplied owner id sees none.
2. `GET` the plan and require identical immutable fields (file, recording, role, size, sha256, epoch, part count). A different epoch is `needs_orchestrator: epoch_changed`; native never adopts a new epoch.
3. Server state gates every PUT: only `uploading` may send bytes. `reserved` triggers a server `reconcile`; `completing` is only ever settled by `reconcile` (no PUT, bounded polling); `completed`/`verified` finish the task; anything else is `needs_orchestrator`.
4. Expired or rejected signature (HTTP 403, or a cached URL within 30 s of expiry): pause for authenticated renewal through `parts/sign`. Signed headers may not contain `Cookie`/`Authorization`/`Origin`; the signed `Content-Length` must equal the planned part length. URLs are checked against the frozen offset/length and are https (`http` only with the explicit emulator-only switch **and** a loopback/emulator-alias host: `127.0.0.1`, `localhost`, `10.0.2.2`, `[::1]`).
5. A PUT whose outcome is unknown (timeout, reset, 5xx, 2xx without ETag, process death mid-PUT) is repeated **only** after a server `reconcile` shows the plan still `uploading` at the same epoch, and only for the same source/part/epoch. There is no receipts-list route, so the repeat is an idempotent S3 part overwrite.
6. A landed part (ETag journaled) is never re-sent; its receipt is re-reported idempotently (`PUT parts/receipts`, at most 32 per request). Completion is requested only when every part is acknowledged; `completeSent` is journaled first so a lost reply is reconciled, never repeated blindly.
7. Cookies are the same Better Auth cookies as Dart, stored only in an Android-Keystore AES-GCM vault (`session.enc`), sent only to the exact configured HTTPS origin, never on provider PUTs, redirects are never followed. A monotonic `sessionRevision` stops a stale Dart push from overwriting a newer native `Set-Cookie` rotation (an equal revision is refused too: a lower revision is `stale_session_revision`, an equal revision with different cookies is `session_conflict`, an equal revision with identical cookies is an accepted no-op, and a refused bind never touches the gate); Dart adopts native rotations through `exportSession`. Every control client is bound to its expected owner and origin and to a **session lease** (in-process epoch + revision): the cookie read and the `Set-Cookie` ingest both require the lease to still be current, so a late response after logout, an owner or origin switch, an A→B→A re-bind or a newer revision of the same session is dropped and a foreign owner's cookie is never sent (the request is refused locally with `owner_changed`). A `Set-Cookie` with a `Domain` attribute is skipped on its own; the other cookies of that response still apply.

## Bridge (`ai.stateaction/native_upload`, schemaVersion 1)

`capabilities`, `bindOwner`, `verifyOwner`, `exportSession`, `unbindOwner`, `setPolicy`, `setCaptureActive`, `enqueue`, `resume`, `pause`, `cancel`, `status`. All except `capabilities` reply `feature_gated` unless the merged manifest sets `ai.stateaction.native_upload.enabled=true` (plugin default `false`). `ai.stateaction.native_upload.allow_cleartext_loopback` (default `false`) permits `http://` only for the loopback/emulator-host origins in emulator tests. Arguments are parsed strictly with bounded lengths; int64 values travel as decimal strings; replies never contain URLs, cookies (except `exportSession`) or local paths. Task states: `queued`, `running`, `waiting_policy`, `backoff`, `needs_visible_resume`, `needs_orchestrator`, `blocked_owner`, `source_blocked`, `uploaded`, `failed`.

## Logout and capture-pause priority fence

`unbindOwner` and `setCaptureActive` bypass the single normal executor. Exact guarantees (JVM-tested for `GateStore`/`SessionJar`/engine; the runtime orchestration is emulator-gate, not yet run):

1. **Immediate, in memory, lock-free (platform thread, at receipt, after argument validation):** `GateStore.fenceOwner()` bumps an atomic sequence; `GateStore.read()` (also lock-free, so a gate `fsync` cannot block it) then reports no owner and a higher generation, and the persisted `invalidationFloor`. `SessionJar.fence()` makes `lease`, `cookieHeader` and `ingest` refuse, so no cookie is attached and a late `Set-Cookie` is dropped. The active run and every in-flight `verifyOwner` request are cancelled. Every engine effect guard re-reads the gate, so no control request, PUT start or chunk begins afterwards (an already-sent request cannot be recalled; its response is dropped). This does not depend on any queue or on disk.
2. **Durable, on a dedicated priority thread:** write-ahead marker `gate.v1.json.fence` (bytes, fsync, directory fsync) -> gate commit -> vault clear -> retained work marked `blocked_owner` -> OS job cancelled. Only when all of these are recorded is the overlay released and the marker removed. **The method reply (ack) is sent after that boundary.** Before the marker is durable there is no restart claim; the in-memory fence holds for the live process.
3. **Failure/restart:** if any durable step throws, the reply is an error, the overlay stays (effects remain blocked in this process) and the marker, if written, stays. On start a surviving marker loads the gate as unbound / capture-paused, fences the jar and forces recovery before any bind or effect. A timeout on the Dart side is **not** a durable invalidation and does not permit a new bind: `bindOwner` while an invalidation is pending or failed returns `invalidation_pending` (after a bounded 15 s wait for the in-flight cleanup).
4. **Stale normal work:** `bindOwner` and `enqueue` capture the call's receipt order and the gate fence sequence; one that predates an invalidation is refused (`superseded` / `owner_changed`) and, being serialized with the cleanup by one runtime mutation lock, cannot install a vault/gate after it. A bind blocked in an `fsync` cannot clear a newer overlay or marker: only an invalidation's own cleanup releases it, and an older cleanup never releases a newer one. `invalidationFloor` (optional `fenceRevision` decimal string on `unbindOwner`, persisted, never lowered, not reset by unbind) refuses any `bindOwner` whose `sessionRevision <= floor` with `stale_session_revision`.
5. **Capture:** `setCaptureActive(true)` fences in memory at receipt, cancels the active run, then persists (marker, gate, scheduler cancel) before the ack. `setCaptureActive(false)` is ordered on the same thread and clears only pauses up to the sequence it observed at receipt; a newer pause survives, and release never starts a job.

The marker file is read with a 3-byte bound and must be a non-empty duplicate-free subset of `u`/`c`; any other existing content (empty, unknown byte, oversized, unreadable) blocks both owner and capture. A marker that cannot be written or removed with certainty is never reported as durable/removed (`lastUnbindMarkerDurable`; an uncertain removal keeps binds refused until a retried unbind completes). Queued calls are admitted by taking the gate-sequence snapshot first and the invalidation-receipt counter second (`CallFence`), also for `verifyOwner` and `resume`. If the bridge attaches to a process whose runtime already exists (job/worker started it) the existing singleton is fenced without disk access; if none exists there is no active transfer to cancel and the priority thread builds it, completes any pending recovery, then runs the invalidation before the bind/enqueue/resume/verify calls queued earlier can take effect (they are refused as superseded).

Not guaranteed: a durable-failure with no writable disk at all cannot persist anything; the process is fenced while alive and the next start is protected only if the marker landed.

## Emulator OS qualification harness

Build `:stera_recorder:assembleDebugAndroidTest` with `-Psa57Qualification` under the resource guard. That build uses the dedicated `open.fpvlabs.stera.upload.qualification` package. Its test manifest enables the native upload gate and loopback cleartext. Both settings default to false in production.

The driver requires one verified emulator, the production web and server builds, and `E2E_EXTERNAL_FIXTURES` pointing to the bounded PostgreSQL and SeaweedFS fixtures. The example below uses API 33. Use `emulator-5580` and `--api 35` for UIDT.

```sh
agent-resource run -- node scripts/mobile/sa57_os_driver.mjs \
  --runtime "$PWD" --serial emulator-5582 --api 33 \
  --test-apk apps/mobile/build/stera_recorder/outputs/apk/androidTest/debug/stera_recorder-debug-androidTest.apk \
  --scenario complete
```

Other scenarios are `policy`, `capture`, `logout` and `expiry`. The driver verifies user 0, installs the dedicated APK for that user, and removes it after the run. It sends test sessions and API-issued plans to app-private storage, prepares loopback access, and starts each phase with Android instrumentation. The tests pass encoded calls through the production Kotlin MethodChannel handler and exercise the platform scheduler, Keystore, confined file reads and HTTP transport. The driver verifies receipts and checks the completed object's length and SHA-256 directly against the fixture. Skipped instrumentation phases fail the scenario.

In the process-death case, the test process signals itself with SIGKILL after the driver verifies a live partial checkpoint. The driver checks that the PID exited, observes scheduler progress, and uses visible Resume if work remains. The expiry case injects an S3 expired-signature response for a real signed URL and requires renewal through the API. Task Manager stop, reboot, and expiry after the provider's actual TTL need separate evidence.

## Evidence and gates

The initial implementation passed 28 Flutter tests and 138 JVM tests. The follow-up on the former SA-18 base passed 76 upload JVM tests and 28 Flutter tests. These tests cover the uploader state machine, source identity and bridge arguments.

The local emulator run records sanitized phase results, the scheduler decision after process death, and provider receipt and object checks under the ignored `artifacts/emulator-verification/` directory. The process-death, capture and logout cases hold later parts at a loopback proxy while the first part lands. At the transition the proxy closes those connections and allows new attempts. The logout check then verifies that no new PUT starts and the incomplete provider upload keeps the same parts.

Open qualification includes physical foreground and suspension, Task Manager stop, reboot, Doze, real Google sign-in, actual signed URL expiry, R2 and 1,000-part volume. SA-22 owns the Dart orchestrator integration. Enabling native uploads requires a reviewed build.
