# Mobile app implementation

StateAction.ai · 2026-10-31 · Implementation target, not shipped behavior. The [capture/upload audit](mobile-capture-and-upload-readiness.md) identifies current native gaps. This specification covers the Flutter collector and Android/iOS native adapters; [capture format](capture-format.md), [shared contracts](../contracts.md), [uploads](mcap-upload.md), [auth](auth-and-access.md) and [local qualification](local-development.md) remain authoritative for their respective protocols.

Implementation update, 2026-11-01: the migrated Android recorder now has an opt-in H.264 adapter and local capture→CPU→Rerun harness. See [implementation and reproducible checks](android-h264-implementation.md) for exact scope, build flags and remaining gates. This does not complete the auth, upload or production qualification requirements below.

## Scope and ownership

Deliver Google login, capture setup/preflight, foreground recording, a persistent own-recordings/upload queue, recovery, upload policy and account/logout controls. The mobile app collects source evidence; the web console performs staff review and dataset assignment. No mobile review, model inference, cloud credentials or direct database client is required.

Pin Flutter `google_sign_in` 7.2.0 and exchange its native Google ID token through Better Auth's existing ID-token flow, then fetch server-verified `/api/v1/me`; [auth](auth-and-access.md#sessions-and-offline-ownership) owns audiences, cookies and signed-build configuration. Default transfer policy is Wi-Fi only and charging required; expose both settings and persist an explicit collector override. Pause uploads during active capture for the initial profile, then resume only when ownership/network/charging conditions permit. This avoids making unqualified simultaneous acquisition/transfer part of the pilot.

| Layer | Responsibility |
| --- | --- |
| Flutter `apps/mobile` | Auth/session adapter, capture controls, validated profile selection, owner-bound local catalog, API client, transfer policy, queue/progress/error UI and explicit local deletion |
| Native `packages/stera_recorder` | Capability probing, camera/AR/independent sensor acquisition, hardware encoder, clock/frame mapping, bounded queues, MCAP writing, close/recovery evidence and native lifecycle handling |
| Native uploader adapters | File-backed/streaming bounded multipart I/O, durable task/part journal, OS scheduling and persisted retry policy; never finalize provider uploads directly |
| Shared contracts / Node API | Versioned commands/manifests, identity/access, recording/file allocation, immutable inventory and transport plans, signing, reconciliation/completion and job admission |
| Python processor | Versioned JPEG/H.264 decoding, integrity checks, hands, clip media/maps, QC and RRD; the phone does not generate training labels or RRD |

Keep frames, encoded payloads, depth buffers and high-rate samples native. Flutter receives bounded typed status/events, not per-frame image bytes. Native acquisition is independent of Dart responsiveness.

## Collector screens

Use the existing Flutter theme/components, with Record, Recordings and Account entry points; no React/Rerun runtime belongs on the collector phone. Existing HTML collector mocks are illustrative and do not qualify the new native controls.

| Screen | Required behavior |
| --- | --- |
| Login / access pending | Native Google login, cancelled/failed login retry, pending/denied enrollment and same-owner reauthentication; offline entry only with retained verified eligibility |
| Record setup | Camera permission, supported requested recording quality, available sensor summary, storage/health readiness and a clear Start or reason it is blocked |
| Recording | Preview, actual elapsed time, concise storage/health/capture warning and Stop; keep awake and prevent account switch or conflicting Start |
| Finalizing / recovery | Visible saving progress and truthful success/error; no Upload-ready label before native close, stable-byte hash and required-file checks |

Keep technical codec/schema diagnostics in support details, not the collector's normal decision flow. Error text distinguishes unsupported device, low storage, waiting for Wi-Fi/charging, interrupted capture and expired login without exposing credentials or provider URLs.

## Capture profile and evidence

Use schema **`stateaction.capture.v1`** and RGB profile **`h264_mcap_v1`**. The initial pilot requests **1920 × 1080 at 30 fps**; these are requested settings, not a claim that every device supports them. Classify existing JPEG recordings as **`jpeg_mcap_v1`** for legacy decoding, retaining unknown provenance explicitly. New captures never silently switch to JPEG, lower resolution/rate or software encoding.

Before Start, native capability negotiation returns requested, supported and accepted settings, hardware encoder identity and unavailable/conditional streams. Unsupported required settings return a structured failure and leave capture idle. A deliberately selected alternative requires its own explicit profile/revision and renewed preflight. Record the accepted profile/config digest, actual raster/rational rates, bitrate/GOP/profile-level and device/OS/app/native revisions. The [capture format](capture-format.md) owns the candidate encoder defaults and clock mapping; implement those settings rather than another platform-specific preset. They remain unqualified until measured. Runtime observations report actual saved rates/counts; configuration alone is not evidence.

| Stream/evidence | Saved content |
| --- | --- |
| RGB, required | H.264 plus an acquisition record for each submitted source frame: unique source frame ID, original capture time/clock, encoder PTS mapping, saved raster/geometry revision and eventual written/drop outcome |
| Accelerometer / gyro, required | Independent raw event streams, initially requesting 100 Hz each, with each event's original timestamp, clock, units, axis/frame convention and requested/effective sampling settings. Do not combine latest samples into invented simultaneity or substitute gravity-removed fused motion for raw acceleration |
| Camera geometry, required | Intrinsics matching saved pixels; original/output raster and crop/resize/rotation/mirror transforms; optical coordinate frame; calibration revision; distortion/extrinsic source and availability |
| Pose/tracking | Native estimated pose with timestamp, coordinate convention, origin/reset events and tracking state. RGB continues during tracking loss; unavailable pose remains unavailable |
| Depth/confidence, conditional | Enabled/supported/observed states, native precision/units, source kind, validity, its matching confidence stream if exposed, original timestamp or explicitly documented association, and matching depth calibration. Initial depth request is 30 Hz where available; record actual unique events/rate and do not duplicate/resample low-rate depth into invented new samples. Estimated/raw-depth API output is not ground truth |
| Camera metadata / optional derived streams | Preserve exposed exposure/focus/sensitivity/readout metadata with units/source; explicitly mark unavailable. Fused motion, point clouds/meshes and assumed covariance/calibration remain separately labelled derived/assumed, including snapshot semantics |
| Acquisition/writer evidence, required | Attempted/submitted/written counts, intentional sampling and gaps, drops/reasons, stream boundaries, encoder/writer errors and final close outcome. Topic registration does not prove samples exist |

The capture profile fixes requested rates, conditional-stream defaults and the candidate H.264 configuration; the device qualification matrix determines which exact configurations may ship. Do not infer cross-platform equivalence from existing Flutter defaults. If a required sensor is unavailable, reject that device/profile; optional unsupported fields remain explicit. No audio/GPS expansion or metric-trajectory accuracy claim is introduced.

## Native video and timing path

Camera acquisition → hardware encoder → complete encoded frame/access unit → Foxglove **Protobuf `CompressedVideo`** message → indexed MCAP. Use `format = "h264"`, Annex B NAL units, **no B frames**, and SPS/PPS available with each IDR keyframe. A native callback may emit configuration or partial buffers: assemble one complete frame before writing its video message; do not treat every callback as a video frame. Convert platform-specific length-prefixed output where necessary without changing encoded image content. The [Foxglove schema](https://docs.foxglove.dev/docs/sdk/schemas/compressed-video) defines interoperability requirements.

Write exact schema name `foxglove.CompressedVideo`, Protobuf schema/message encoding and a complete embedded descriptor set, including timestamp dependencies. Because new video messages coexist with legacy CDR sensor channels, MCAP uses the generic empty Header profile, not `ros2`. Follow the capture-format schema/channel definitions; importing a Protobuf video topic cannot imply every channel has a ROS 2 CDR encoding.

`CompressedVideo.frame_id` names the coordinate frame; it is **not** the unique source frame ID. Store acquisition identity/geometry/clock mapping in the versioned companion schema, referencing the video channel/message sequence and encoder PTS. Preserve native capture time as an integer in its own clock domain; separately record encoder PTS/time base and MCAP log time using the shared fixed session anchor policy. No float-second round trip, encoder-completion timestamp substitution, wall-clock reordering or unmeasured cross-sensor synchronization claim. The worker joins by explicit IDs/mapping, not nearest timestamps.

Use one serialized writer authority and bounded per-stream queues. Encoder/video backpressure cannot drain and discard the independent IMU queue. When an event cannot be retained, persist its identity/time range and reason where known, and mark incomplete/unknown evidence when even drop accounting cannot be written. A required writer/encoder failure initiates controlled stop; never report successful complete capture after silently losing a required stream. Counts become written only after writer acceptance; file integrity remains provisional until close. Configuration/calibration transitions are versioned; an unexpected encoder format reset stops the take unless the profile explicitly supports a declared decoder-safe segment.

Record only while camera access is available. Backgrounding, screen lock, camera interruption, thermal shutdown or app termination must be represented honestly; foreground camera capture is the pilot target. Preserve already acquired samples, stop/drain/close if execution permits and explain the interruption. The initial profile uses Start/Stop; an interrupted take ends, and recording again starts a new identity. Do not retain an ambiguous in-take Pause that hides missing time or silently resets codec/clock state.

Keep the screen awake only during active foreground recording and restore normal idle behavior afterwards. Freeze the encoded raster for the take; UI rotation cannot silently reconfigure the encoder or invalidate calibration. Preflight checks camera/motion permissions, profile support, storage reserve and health; denial returns a clear blocked state without creating a false successful take. Screen power and mounted-phone heat are part of the two-hour device measurement.

## Flutter/native contract

Materialize a small typed Dart/Kotlin/Swift bridge contract in the shared conformance fixtures. Adapt existing channels rather than shipping a second recorder. The names below are semantic operations; freeze exact channel/method names once during implementation.

| Operation | Required behavior/result |
| --- | --- |
| `getCapabilities(profileRequest)` | Validate schema/config, device and permission availability; return accepted settings or explicit unsupported reasons; probing cannot create a capture |
| `startCapture(commandId, clientRecordingId, ownerId, permissionRef, acceptedProfile)` | Revalidate accepted config/capabilities, persist native/local ownership and start identity before sensor writes; reject conflicting active take or changed unsupported config; return capture/session identity and accepted settings |
| `getCaptureSnapshot(clientRecordingId)` / `listRecoverableCaptures()` | Return authoritative state, bounded counters, inventory and latest durable event sequence after Dart/native relaunch |
| `stopCapture(commandId, clientRecordingId, reason)` | Idempotently enter finalization; acknowledge completion only after encoder drain, writer close and final inventory persist; an early metadata file is not closure |
| `recoverCapture(clientRecordingId)` | Inspect an interrupted artifact and return recoverable/incomplete/quarantined state; do not mutate a previously sealed source or claim success from a trailing magic check alone |
| `applyUploadPolicy(policy)` / `pauseTransfers(ownerId)` | Persist policy and stop scheduling new work; on logout cancel owner-bound in-flight tasks where possible and reconcile uncertain outcomes later |
| `resumeTransfer(fileId, transportEpoch, plan)` / `getTransferSnapshot()` | Run only an owner-authorized API plan; recover native task/part state and report bounded progress; APIs own URL allocation and completion |

Every event has `schemaVersion`, local capture/transfer identity, monotonically increasing persisted `eventSequence`, `kind` and typed payload. Event kinds cover capture state, capability/config rejection, sampled counters/health, interruption/error, finalization outcome, transfer state/progress and authorization required. Include stable `code`, `retryable` and user-safe message on failures. IDs, nanoseconds, byte counts and large counters cross bridges/HTTP as decimal strings where needed; no unsafe Dart→JavaScript number conversion. Validate caller-supplied paths against the app-owned source inventory. Command replay returns existing state; changed content under the same command/capture identity conflicts. Event delivery is a UI hint; durable snapshots/journals recover missed events.

## Capture state and local files

Capture lifecycle: **idle → preflight → recording → finalizing → finalized**. Unsupported settings/preflight failure return to idle without a take. A runtime interruption enters finalizing when safe; an unclosed process loss becomes **recovery_required** on next launch. Failed/corrupt/unrecoverable sources are **quarantined**, retained and clearly distinguished from finalized files. Store `container_state` separately from `capture_outcome`: an early interrupted take with clean EOS/close and complete integrity evidence may upload as a shorter interrupted recording. Unclosed/malformed/unresolved-frame artifacts cannot. Staff/processor QC decides usefulness; a closed interrupted take never masquerades as an uninterrupted two-hour success.

Start persists owner ID, `clientRecordingId`, permission reference, accepted profile and app-relative session directory. Keep a native transaction/journal for capture identity/state and written/outcome evidence; Flutter's catalog is a projection, not a competing writer. Atomically persist close outcome and inventory after draining hardware encoder output, flushing MCAP messages/indexes/footer and closing every required sidecar. Reset all session-local calibration/depth/encoder flags for every take.

Each finalized session contains the MCAP, final `metadata.json` and all declared required evidence/calibration sidecars. Frame/evidence rows may be bounded shards or MCAP messages; the final metadata lists exact files/roles/requiredness and schema references. Optional thumbnail is never a substitute for RGB. File names/paths are app-relative, stable across app-container relocation, and cannot escape the session root. Exclude captures from platform cloud backup and preserve platform file protection compatible with qualified locked-device transfer.

After native close acknowledgment, stream **actual file bytes** through SHA-256 using bounded buffers, comparing identity/size before and after hashing. Persist the hash/length/immutable inventory; a path+size hash or multipart ETag is not a content hash. A concurrent mutation invalidates readiness. Hashing/finalization interruption resumes through validation; never upload a still-growing file. Repair cannot overwrite a sealed artifact: any repair that changes bytes creates a new logical file/capture identity and records provenance to the retained original. No automatic truncation, silent salvage or deletion of an interrupted source.

## Auth and account ownership

Use the shared Better Auth Google flow and platform secure session storage; qualify provider audience/nonce, callbacks and rotation on signed devices. Native requests use the shared session/header rules. Persist immutable verified owner identity **at capture start**. Previously authorized collectors may capture offline under their pinned identity; network resume rechecks live eligibility. Unenrolled/unauthenticated users cannot upload. Legacy ownerless captures require explicit operator-assisted recovery.

Session expiry pauses API/URL renewal and requests one serialized reauthentication; a network error and an expired signed URL are different states. Logout stops scheduling and renewal, requests native cancellation, preserves files/journals and clears credentials; remote revocation is confirmed only when acknowledged. Already issued URLs can remain usable until expiry, so reconcile any in-flight uncertain parts on the original owner's next login. Do not allow account switch during an active take without first stopping/finalizing it. A different account cannot view, resume or adopt another owner's queue.

## Resumable upload and device policy

Transfer lifecycle: **local_ready → preparing → uploading → completion_pending → uploaded → verifying → verified**. Orthogonal pause reasons include user, Wi-Fi/charging policy, storage, authorization and retry delay. Retryable failure preserves the same identity/receipts; terminal conflict or unknown provider state requires reconciliation/attention. Cloud processing/review status is fetched separately: uploaded is neither source-verified nor approved.

Use exactly the [existing API upload surface](mcap-upload.md#http-surface). Register owner-bound recording, allocate files, seal the full inventory, request signed part ranges, upload direct to private R2, journal receipts, reconcile and ask the API to complete. Sealing and upload completion can arrive in either order; the API admits exactly one job once every required file is complete. The device never calls provider Create/CompleteMultipartUpload, picks object keys or holds storage credentials.

Initial transport qualification target: **64 MiB fixed parts**, one source at a time, **two concurrent PUTs**, at most **three temporary chunks / 192 MiB** plus measured journal/OS overhead and safety reserve. Small files use one-part multipart. Persist server-frozen offsets/lengths, expected `transportEpoch`, exact ETags/bytes and native task IDs; do not adapt part geometry on resume. Recover progress via fully paginated provider reconciliation through the API, renew expired URLs and retain landed parts. Only a confirmed retired unfinished transport can restart at a fresh epoch; old-epoch receipts cannot complete it. The source cap is **100 GiB per file**, with a two-hour pilot target; these are admission limits, not proven device capacity.

Both native adapters own durable retry attempts/next-attempt time and bounded backoff; suspended Dart cannot be the sole retry authority. An unreadable source/extraction failure stops that source rather than immediately selecting the same part in a hot loop. Expired URLs pause for API renewal; repeated provider/network failures yield a visible paused/failed state. Hold OS background execution completion until its actual bounded work/checkpoint finishes; reattach native task delegates/journals after relaunch. iOS uses file-backed background transfers; force-quit/relaunch limitations must be visible. Android needs a real OS-scheduled/foreground-qualified upload implementation: the current code's unsupported guard is a release blocker, and a notification alone does not implement transfer.

Use an owner-bound **native control API client** while Dart is suspended: it reads the same secure session, applies cookie rotation, and calls only the existing sign/receipt/reconcile/complete routes. It never holds provider credentials or completes an MPU directly. Serialize it with Flutter auth/control calls; expired/revoked auth pauses and requires interactive same-owner login. Never store Google/session tokens in the part journal. Native URL renewal is a real acceptance case, not a promise based on long-lived pre-signed URLs.

Android API 34+ uses a `JobScheduler` **user-initiated data-transfer JobService** scheduled by explicit Upload/Resume while the app is visible. Declare `RUN_USER_INITIATED_JOBS`/service binding, progress notification, network/charging constraints and estimated remaining bytes; run the multipart engine off the main thread, checkpoint on stop and finish only after actual work/checkpoint completion. Older supported Android uses unique WorkManager `CoroutineWorker` foreground `dataSync` work over the same engine/journal. For unattended recovery when a user-initiated job cannot legally start, use short interruptible reconciliation/work windows or display Resume; Task Manager Stop/reboot must recover from the journal. UIDT avoids ordinary job quotas but is still stoppable; neither scheduler promises unlimited background runtime. [Android UIDT](https://developer.android.com/develop/background-work/background-tasks/uidt), [WorkManager limits](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running)

Default bulk uploads to Wi-Fi only and charging required; expose explicit overrides, persist them and show the reason when waiting. Pause transfers during active recording for the initial profile. Preflight and continuous checks account for remaining source growth, finalization/journal needs and bounded upload scratch. Low storage, critical battery/thermal state or source-cap proximity initiates a reasoned stop early enough to finalize; establish device-specific reserve/warning thresholds by measurement. Never silently lower capture fidelity or evict pending sources. Charging can increase heat; the same health policy still applies. Do not delete a temporary chunk still referenced by an active or uncertain native task.

No automatic local cleanup on successful PUT/completion. Keep pending, failed and unverified sources. After server content verification and confirmed retained cloud copy, offer an explicit per-recording deletion confirmation with bytes freed, as defined by the upload retention policy. Cancelling upload does not delete source; deleting local source does not delete cloud data. Diagnostics include IDs, versions, counters and safe errors, excluding credentials, signed URLs and private payloads.

## Implementation order and handoff

1. **Contracts and fixtures:** freeze capture/profile/bridge schemas, required versus conditional streams, clocks/geometry, final inventory and current versus legacy decoder identifiers. Commit small valid, unsupported, dropped-frame and interrupted fixtures; no native merge before this boundary agrees with the worker.
2. **Native capture integrity:** fix independent raw IMU, rate/toggle handling, saved-raster calibration, consecutive-session reset, tracking-independent RGB, accurate write/drop evidence and close/recovery. Add hardware H.264 adapters and complete-access-unit/config mapping; preserve the JPEG reference fixtures.
3. **Durable collector/auth:** ownership, secure session rotation, capability/error UI, native recovery snapshots, final byte hashing and immutable file catalog. Remove any path+size content-hash assumption.
4. **Transport parity:** reviewed iOS reuse with corrected retries/background completion; implement Android adapter; connect both to the same API plans, epoch/reconciliation and bounded disk/network policy.
5. **Qualify and enable:** complete the device and local-pipeline gates below, record approved device/config matrix and measurements, then enable the profile for field collectors. Do not mark format support as proven because a desktop decoder opens one sample.

Coordinate source changes with the engineer fixing `stera-app`; do not move the active checkout during those fixes. The [monorepo plan](monorepo.md) imports mobile and the required native recorder together, preserving capture IDs, DB migrations, app/signing IDs, journals and upstream licenses. The full Python Stera SDK is optional reviewed/reference or worker-only reuse where necessary; it is not a mobile runtime/backend dependency. Record import commit and handoff owner before removing submodules or legacy server assumptions.

Version local database migrations and preserve pending legacy rows/files. Existing adaptive part plans cannot be silently rewritten to 64 MiB. Legacy ownerless captures or transports created by the old backend enter explicit recovery/attention: prove ownership and reconcile or retire the old authority's MPU before allocating a new API transport. Never adopt an old queue into the newly signed-in account, reuse an unverified provider key or delete uncertain source bytes during cutover.
