# Catalog schema and integrity (SA-13)

Implemented in `packages/server/migrations/002_auth.sql`, `003_catalog.sql` and the access layer `packages/server/src/catalog/`. Postgres 17. No releases table: the Dataset-version follow-up adds it with a new migration.

**Seal and completion order.** Upload completion and sealing may happen in either order. Seal locks the recording row and freezes the declared live source inventory: exactly one `source_manifest`, one required `source_mcap`, and at least one required `recorder_metadata`. It also pins the manifest's declared SHA-256. Source-file inserts lock and recheck the recording (`FOR SHARE`, unsealed only), so no file can join after a concurrent seal commits. An identical seal replay returns the existing seal; a different manifest conflicts; a replay never rewinds status. Job admission (`createProcessingJob` and the `jobs` insert trigger) requires the frozen required files to be completed. Output-file inserts likewise lock and recheck the job, so none land after acceptance commits.

**Logical-file retirement versus transport restart.** A source file entering `cancelled`/`failed`/`expired` retires the _logical_ file: it leaves the live inventory and a replacement may be reserved. That is allowed only before seal. The `files` trigger locks the recording row (`FOR SHARE`) on any such transition and rejects it with `SAC04` once `source_manifest_file_id` is set, so the frozen inventory cannot shrink and no job can be admitted without a declared required file. A cancel racing a seal serializes on the recording row in both orders: cancel first means the waiting seal re-reads the inventory and is rejected if it is incomplete; seal first means the waiting cancel sees the seal and fails. Rows retired before seal remain excluded from the inventory. After seal, a broken, aborted or expired _transport_ (multipart upload) is recovered on the same logical file by advancing `transport_epoch` with a new object key and provider upload; the file stays live. A seal pointer also always takes the recording out of `registered`/`uploading` (row CHECK plus trigger), including in the sealing statement itself.

Errors use SQLSTATE `SAC01` immutable, `SAC02` not approved, `SAC03` stale revision/sequence, `SAC04` lifecycle state, `SAC05` not authorized; `src/catalog/errors.ts` maps them (and unique/FK/check violations) to v1 HTTP error codes.

## Lock order

All catalog writes run in READ COMMITTED. Review and membership mutations take, in order:

1. clip locks through `catalog_lock_clip(uuid)` (transaction advisory lock, no UPDATE privilege needed), sorted by clip UUID;
2. dataset rows `FOR UPDATE`, sorted by dataset UUID;

then recheck the latest review and expected revisions before writing. The review and membership triggers take the same clip lock, so a direct insert that read stale eligibility waits behind an uncommitted rejection and fails with `SAC02` once it commits. Approval with `datasetSelection` locks current ∪ selected datasets, checks every expected revision, appends the review, applies the diff and advances changed revisions in one transaction; rejection removes all memberships first and advances each affected revision. Bulk adds lock sorted clips, so opposite-order batches cannot deadlock.

Upload lifecycle writes lock the recording row before any of its file rows (`reserveSourceFile`, `sealRecording` and `createProcessingJob` take it `FOR UPDATE`; the `files` trigger takes it `FOR SHARE` on source inserts and source retirements). Seal never locks file rows, so a direct file retirement (file row, then recording) cannot deadlock with it; any future helper that both retires files and touches the recording must lock the recording first.

## Credentials and privileges

Every catalog function sets `search_path = pg_catalog, public, pg_temp` and schema-qualifies relations, so session TEMP objects cannot shadow catalog tables inside triggers or the definer routine. The grant function also revokes `TEMPORARY` on the database from PUBLIC and the app role. Helpers are PL/pgSQL so pinned search paths keep cached plans.

Migrations run with the owner credential only. The owner needs no superuser or CREATEDB (tested as `NOSUPERUSER NOCREATEDB NOBYPASSRLS CREATEROLE`). `stateaction_grant_app_role(role)` grants the restricted web role:

- SELECT on every catalog/auth table; Better Auth tables also INSERT/UPDATE/DELETE;
- INSERT on recordings, files, jobs, clips, reviews, datasets, dataset_clips; DELETE only on dataset_clips;
- column-level UPDATE on mutable lifecycle columns of recordings, files, jobs and datasets;
- no DML on `access` or `dataset_access`, no TRUNCATE, no schema changes, no TEMP objects;
- default privileges reset: earlier broad `ALTER DEFAULT PRIVILEGES` grants to the role on tables, sequences and functions are revoked, so future objects (e.g. a later releases table) are inaccessible until a migration grants them explicitly.

Staff grant changes go through `catalog_set_dataset_access(...)`, a `SECURITY DEFINER` routine the web role may execute. It checks that the actor is enabled staff and the grantee an enabled customer, and it locks the dataset row (lock-order step 2, no clip locks). Grants are independent of membership revisions, so they do not advance `datasets.revision`. The web service never needs owner credentials. Pilot roles in `access` remain an operator task with the owner credential.

The migrator (`src/migrations.ts`) applies ordered `NNN_*.sql` files inside one transaction under advisory lock `7430001`, records each file's SHA-256 and refuses edited applied files. A database bootstrapped by the original 001-only `migrate` adopts the current 001 checksum (reported as `adopted`). It then re-applies the grant function when `stateaction_app` exists.

**SA-14 integration (implemented).** The hosted/dev owner migration (`hosted:migrate`, `packages/server/src/cli.ts`) calls `migrateDatabase({ ownerUrl, appRolePassword })`: `applyMigrations` → `ensureAppRole` (create/password only, never grants) → `stateaction_grant_app_role`, in one transaction. The role name must match `^[a-z_][a-z0-9_]{0,62}$` and is validated before any query (then passed as a bound setting, never interpolated). A pre-existing role fails closed unless it is plain LOGIN: no SUPERUSER, CREATEDB, CREATEROLE, REPLICATION or BYPASSRLS and no membership in other roles; the owner's automatic ADMIN membership in a freshly created role is allowed. No broad grants or default privileges remain. See render-deployment.md.

## Bounded reads

`listDatasetClips` (approved-only grid; customers additionally need an enabled role and a live grant), `listDatasets` (distinct approved counts/duration) and `listInternalClips` (staff All clips with pending/approved/rejected) run as single statements with keyset cursors on exact microsecond timestamps plus UUID (default 24, max 100). Dataset counts aggregate the members of the returned datasets only. Roles are read from the database, not trusted from the caller. Query plans on a 6,000-clip / 36,000-file / 4,000-membership fixture use the membership/review indexes with LIMIT and no catalog table scans. The grid takes about 1 ms; the dataset list takes about 35–55 ms because it counts about 2,000 members of the largest dataset (`server:integration` writes them to `artifacts/catalog-integration/query-plans.json`).

## Seed and tests

`pnpm --filter @stateaction/server seed` (local only) creates collector, staff and two customer identities. With `LOCAL_SEED_PASSWORD`, it also creates Better Auth credential accounts. It also seeds one sealed/processed recording with five clips: pending, rejected, approved in a shared (granted) dataset, approved in a private (ungranted) dataset, and approved in both. Each seeded recording has a manifest, MCAP, recorder metadata and calibration. Rows are catalog metadata only; no media objects are written.

`pnpm exec nx run server:integration` starts a throwaway pinned Postgres on an ephemeral loopback port, then runs migration, constraint, seed, concurrency and query-plan tests as the unprivileged owner and the restricted app role.
