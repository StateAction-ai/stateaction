# Catalog schema and integrity (SA-13)

Implemented in `packages/server/migrations/002_auth.sql`, `003_catalog.sql` and the access layer `packages/server/src/catalog/`. Postgres 17. No releases table: the Dataset-version follow-up adds it with a new migration.

## Tables

| Table                                                 | Identity and constraints                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Better Auth `user`/`session`/`account`/`verification` | Better Auth 1.7.15 default names/columns, verified identical to its generator ([evidence](../validation/sa-13-better-auth.json)). User IDs are opaque text; domain tables reference `"user"` with `RESTRICT`.                                                                                                                                                                                                                                                                                                                                                                                              |
| `access`                                              | `(user_id, role)` key; `collector`/`staff`/`customer`; enabled flag. Operator-managed: the web role can only read it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `recordings`                                          | Unique `(owner_user_id, client_recording_id)`; capture identity columns immutable. `source_manifest_file_id` + `source_manifest_sha256` composite-reference `files(id, recording_id, sha256)`, must be a completed `source_manifest` file, and are immutable once sealed. Sealed states require the pointer. Owner needs an enabled collector role.                                                                                                                                                                                                                                                        |
| `files`                                               | Logical source/output file. Sources: unique `(recording_id, client_upload_id)` plus request digest; outputs: `(job_id, recording_id)` references the job. At most one live `source_manifest` and one live `source_mcap` per recording, both required. Object keys embed recording/job, file ID and transport epoch (`recordings/{r}/sources/{f}/e{n}/…`, `jobs/{j}/outputs/{f}/e{n}/…`) and are globally unique, so no key is reused. Identity columns are immutable; a restart advances the epoch by one with a new key and provider upload; completed transport is closed (only `completed → verified`). |
| `jobs`                                                | One row per attempt; `kind = process_recording` only. `(recording_id, source_manifest_sha256)` references the recording's sealed digest. At most one live job per recording, one successor per `previous_job_id` within the same recording. Recorded nonce/call/workflow/result references are write-once; finished jobs are frozen. `succeeded` requires a completed `result_manifest` of that job with its exact digest.                                                                                                                                                                                 |
| `clips`                                               | Immutable (no update/delete for any role). Unique `(job_id, ordinal)`. Six file slots reference `files(id, job_id)` and must be completed outputs of the matching role; inserted only while the job is `result_pending`. Replaying acceptance returns the same IDs; a different result conflicts.                                                                                                                                                                                                                                                                                                          |
| `reviews`                                             | Append-only. Unique `(clip_id, revision)`; revision must be latest + 1. `(clip_id, job_id)` and `(job_id, result_manifest_sha256)` pin the exact successful result. Reviewer needs an enabled staff role. Approval needs a task label; the submitted selection is stored.                                                                                                                                                                                                                                                                                                                                  |
| `datasets`                                            | Mutable working grouping; every update advances `revision` by exactly one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `dataset_clips`                                       | Key `(dataset_id, clip_id)`; many-to-many. Insert requires the clip's latest review to be approved and a staff actor. A non-approved review cannot be appended while memberships remain.                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `dataset_access`                                      | Key `(dataset_id, user_id)`, enabled, granted_by, permission evidence reference.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

Errors use SQLSTATE `SAC01` immutable, `SAC02` not approved, `SAC03` stale revision/sequence, `SAC04` lifecycle state, `SAC05` not authorized; `src/catalog/errors.ts` maps them (and unique/FK/check violations) to v1 HTTP error codes.

## Lock order

All catalog writes run in READ COMMITTED. Review and membership mutations take, in order:

1. clip locks through `catalog_lock_clip(uuid)` (transaction advisory lock, no UPDATE privilege needed), sorted by clip UUID;
2. dataset rows `FOR UPDATE`, sorted by dataset UUID;

then recheck the latest review and expected revisions before writing. The review and membership triggers take the same clip lock, so a direct insert that read stale eligibility waits behind an uncommitted rejection and fails with `SAC02` once it commits. Approval with `datasetSelection` locks current ∪ selected datasets, checks every expected revision, appends the review, applies the diff and advances changed revisions in one transaction; rejection removes all memberships first and advances each affected revision. Bulk adds lock sorted clips, so opposite-order batches cannot deadlock.

## Credentials and privileges

Migrations run with the owner credential only. The owner needs no superuser or CREATEDB (tested as `NOSUPERUSER NOCREATEDB NOBYPASSRLS CREATEROLE`). `stateaction_grant_app_role(role)` grants the restricted web role:

- SELECT on every catalog/auth table; Better Auth tables also INSERT/UPDATE/DELETE;
- INSERT on recordings, files, jobs, clips, reviews, datasets, dataset_clips; DELETE only on dataset_clips;
- column-level UPDATE on mutable lifecycle columns of recordings, files, jobs and datasets;
- no DML on `access` or `dataset_access`, no TRUNCATE, no schema changes.

Staff grant changes go through `catalog_set_dataset_access(...)`, a `SECURITY DEFINER` routine the web role may execute. It checks that the actor is enabled staff and the grantee an enabled customer, so the web service never needs owner credentials. Pilot roles in `access` remain an operator task with the owner credential.

The migrator (`src/migrations.ts`) applies ordered `NNN_*.sql` files inside one transaction under advisory lock `7430001`, records each file's SHA-256 and refuses edited applied files. A database bootstrapped by the original 001-only `migrate` adopts the current 001 checksum (reported as `adopted`). It then re-applies the grant function when `stateaction_app` exists.

**SA-14 integration contract.** The hosted owner migrator should call `applyMigrations(client)` (or `migrateDatabase`) inside its transaction instead of reading `001_platform.sql`. After provisioning the role, it should call `SELECT stateaction_grant_app_role('stateaction_app')` in place of broad `GRANT … ON ALL TABLES` and `ALTER DEFAULT PRIVILEGES`. Broad grants would reopen DELETE/UPDATE. The triggers still protect the invariants, but least privilege would be lost.

## Bounded reads

`listDatasetClips` (approved-only grid; customers additionally need an enabled role and a live grant), `listDatasets` (distinct approved counts/duration) and `listInternalClips` (staff All clips with pending/approved/rejected) run as single statements with cursor pagination (default 24, max 100). Roles are read from the database, not trusted from the caller. Query plans on a 6,000-clip/36,000-file fixture use the membership/review indexes with LIMIT and no catalog table scans (`server:integration` writes them to `artifacts/catalog-integration/query-plans.json`).

## Seed and tests

`pnpm --filter @stateaction/server seed` (local only) creates collector, staff and two customer identities. With `LOCAL_SEED_PASSWORD`, it also creates Better Auth credential accounts. It also seeds one sealed/processed recording with five clips: pending, rejected, approved in a shared (granted) dataset, approved in a private (ungranted) dataset, and approved in both. Rows are catalog metadata only; no media objects are written.

`pnpm exec nx run server:integration` starts a throwaway pinned Postgres on an ephemeral loopback port, then runs migration, constraint, seed, concurrency and query-plan tests as the unprivileged owner and the restricted app role.
