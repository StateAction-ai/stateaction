# StateAction contracts (v1)

Versioned wire and durable-document contracts shared by the phone, API, workflow controller and processing worker. JSON Schema 2020-12 files in [`api/`](api/) are normative. Three adapters load the same files and run the same fixtures:

| Adapter                               | Location / Nx project                            | Validator                                                                                                         |
| ------------------------------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| TypeScript (`@stateaction/contracts`) | `packages/contracts` · `contracts`               | Ajv 8.20 `Ajv2020`, `strict: true`, `allErrors: true`                                                             |
| Python (`stateaction-contracts`)      | `packages/contracts/python` · `contracts-python` | `jsonschema` 4.26 `Draft202012Validator`, with ECMA-262 end-of-input `$` semantics                                |
| Dart (`stateaction_contracts`)        | `packages/contracts/dart` · `contracts-dart`     | `json_schema` 5.2.2, draft 2020-12; pure Dart (no `dart:io` in `lib/`), so Flutter can supply schemas from assets |

Capture-format schemas (`capture/`, MCAP channels, codec/video and sensor fixtures, capture Profile/Close/evidence documents) are owned by SA-50 and are not part of this package's v1 API surface. They can reference the shared definitions in [`common.v1.schema.json`](api/common.v1.schema.json) by absolute `$ref`, for example `https://stateaction.ai/schemas/common.v1.json#/$defs/timestampNs`.

**Capture bridge ownership.** This package owns the generic Flutter/native capture bridge boundary under [`api/native/`](api/native/): the command, snapshot (status and event payload), error, capability-result and recoverable-list documents, and their shared positive and negative fixtures. The detailed profile and evidence schemas these documents reference by `profileRevision` and `captureConfigSha256` belong to SA-50. Binding the documents to actual Kotlin/Swift/Dart channels belongs to the native recorder tickets (SA-18 for finalization and hashing, SA-51 for the Android H.264 recorder). No native recorder integration is claimed here. Frames, encoded payloads, depth buffers and high-rate samples never cross the bridge.

## Contracts

[`api/catalog.v8.json`](api/catalog.v8.json) is the current registry. It lists each contract: its schema, casing, version discriminator, byte bound and cross-field rules. Each registry revision is an exact superset of the previous, published and immutable one: [`api/catalog.v1.json`](api/catalog.v1.json) (SA-12), [`api/catalog.v2.json`](api/catalog.v2.json) (adds only `http.me.v1`, SA-15) [`api/catalog.v3.json`](api/catalog.v3.json) (adds only `http.recording-registration.v1`, SA-19) and v4 [`api/catalog.v4.json`](api/catalog.v4.json) (adds only `http.profile-update.v1` and `http.profile.v1`, SA-16) v5 (adds only `http.output-create.v1` and `http.output-plan.v1`, SA-20) and v6 (SA-71: `artifacts.simulation-provenance.v1`, `http.simulation-provenance.v1`, `artifacts.recording-source.v2`, `http.recording-create.v2`, `http.recording.v2`, `http.recording-registration.v2`, `jobs.task-input.v2`; see [simulated capture admission](../../docs/components/simulated-capture-admission.md)) and v7 (SA-25 internal job control: `jobs.controller-action.v1`, `jobs.controller-result.v1`, `jobs.reconcile-result.v1`, `jobs.heartbeat-ack.v1`, `http.input-read.v1`; see [job orchestration](../../docs/components/job-orchestration.md)). Every earlier entry is deep-equal. A registry version is not an HTTP route version: v2-v6 additions are served under `/api/v1`, the v7 job-control contracts under `/internal/v1`. v8 (SA-35 dataset catalog and read broker, all `/api/v1`: `http.dataset-create.v1`, `http.dataset-update.v1`, `http.dataset-members-add.v1`, `http.clip-read-create.v1`, `http.dataset.v1`, `http.dataset-page.v1`, `http.dataset-clip.v1`, `http.dataset-clip-page.v1`, `http.staff-clip-page.v1`, `http.clip-read.v1`, `http.dataset-change.v1`; see [dataset access](../../docs/components/dataset-access.md)) adds only those entries; all three adapters load v8.

Deferred to their own tickets, deliberately absent from v1:

- `review/v1` (review), `release-selection/v1` and `release/v1` (dataset versions), and the catalog/browser routes.
- **Export claim grant.** `jobs.claim-grant.v1` is `kind: process_recording` only. An export grant (selection digest, approved output inputs) is a new contract version owned by the export-release ticket. `jobs.task-input.v1` keeps its scoped `export_release` branch.
- **Worker output transport.** Output reservation (`POST /internal/v1/jobs/{jobId}/outputs`), the output part plan and the job output seal are owned by the worker-output ticket. `http.upload-create.v1`/`http.upload-plan.v1` are phone source contracts (they require `recordingId` and a source role) and are not reused for outputs.
- **Upload transition responses.** Each `reconcile`/`complete`/`cancel`/`restart` transition responds with a success envelope whose `data` is `http.upload-plan.v1`. This is stated in the transition schema; route behaviour belongs to the upload tickets.
- **Capture bridge transfer commands** (`applyUploadPolicy`, `resumeTransfer`, transfer snapshots) belong to the native uploader tickets.

### Value encoding

- **Domain IDs** (recording, file, job, clip, manifest) are canonical lowercase UUIDs. **Auth user IDs** are opaque strings (`^[A-Za-z0-9][A-Za-z0-9._~:-]{0,127}$`). They are never parsed and never required to be UUIDs.
- **Byte sizes and offsets** are decimal strings: file sizes 1..107374182400 (the 100 GiB transport cap), byte counts 0..107374182400.
- **Timestamps, PTS, native frame IDs and large counters** are exact non-negative int64 decimal strings (0..9223372036854775807). The bound is enforced by a generated regular expression, so every standard validator checks it identically; `test/policy.test.ts` regenerates and checks the expression. Convert with `BigInt`/`int`/`BigInt.parse`, never floating point.
- **Clocks**: each timestamp names its `clock_domain`. Domains are never merged or converted. A frame map keeps `source_frame_id`, `timestamp_ns`, `clock_domain`, `source_pts`, `clip_pts` and a rational `time_base {num, den}`. `clip_pts = source_pts − first source_pts`. Wall time is RFC 3339 UTC with a `Z` suffix only.
- Part numbers, epochs, counts and raster sizes are bounded JSON integers within the safe range. Every object is closed (`additionalProperties: false`, or a bounded map), every array and string is bounded, and every number has limits.
- **Source manifest.** `sourceFileRole` includes `source_manifest`. After every other source file is closed and hashed, the phone writes the exact `recording-source/v1` declaration bytes. Its `files` list exactly those other files and never the declaration itself (a `source_manifest` entry is `reference_mismatch`; there is no self-hash). The phone reserves and uploads these bytes as role `source_manifest` through the same upload transport, limited to 1 MiB. The seal lists exactly one required `source_manifest` plus exactly the declared files: one required `source_mcap` and at least one required `recorder_metadata`. Otherwise the seal is `inventory_incomplete`. `TaskInput.sourceManifestSha256`, `ClaimGrant.digests.sourceManifestSha256` and `ProcessingResult.source_manifest_sha256` are the plain SHA-256 of those stored bytes. `ClaimGrant.inputs` lists every sealed file, including exactly one `source_manifest` input whose `sha256` equals the pinned digest (otherwise `reference_mismatch`) and exactly one `source_mcap`. The API reads only that ≤ 1 MiB control document: it checks its digest, validates it as `artifacts.recording-source.v1` and calls `checkSealedInventory(seal, declaration)` / `check_sealed_inventory` / `checkSealedInventory`. It never parses media or derives device evidence. `verified_sources` in the result lists the declared (non-manifest) files, unique by `file_id`.
- **Image identity.** `imageSpecSha256` / `image_spec_sha256` is the SHA-256 of the locked worker image build specification, as recorded by our build tooling. It is not a Modal image ID or an OCI registry digest, and it does not imply provider attestation.
- **Signed URLs** match `^https?://[!-~]+$`: printable ASCII only, so whitespace, control and non-ASCII characters (U+0085, U+001C, U+FEFF, `é`) are rejected identically in every adapter. Patterns never use `\s`, `\d`, `\w` or an unescaped `.`, because their meaning differs between ECMA-262 and Python `re`. `test/policy.test.ts` enforces this.
- **Wall time** enforces month-specific day ranges (`2026-02-31` and `04-31` are rejected). February 29 is accepted in every year because leap years are not checked. Deadline ordering compares exact instants, including fractions.
- **Frame maps and sensors.** A frame-map row carries RGB frame identity (`source_frame_id`, unique), its named clock and PTS. Sensor association is not duplicated in v1 rows: capture `SensorEvent` records (SA-50) name `association_source_frame_id` explicitly, or null, and consumers join on that exact ID. Nearest-timestamp joins are never used.
- **3D hands**: `points_3d.space` is either `model_relative` (`metric_accuracy_validated: false`, units `model_estimated_meters`, origin `hand_geometric_center`) or `camera_metric` (`metric_accuracy_validated: true` plus a validation profile and evidence file reference). The metric branch is reserved for a future separately qualified profile. Its metadata is checked for shape only, and the presence of evidence fields does not prove physical accuracy. Production output stays model-relative, and the result manifest pins `metric_accuracy_validated: false`. Image landmarks are 21 `(x, y)` pixels in `joint_order`. Missing points are `null` with mask `false`, `handedness_score` is not per-joint confidence, and visibility is always `"unknown"`. The NPZ descriptor has eight arrays. `handedness` is `int8 [F,2]`: `0` left, `1` right and `-1` none, exactly where `hand_detected` is false. A detector slot index never implies a side, and two slots may predict the same side.
- **Results and failures.** `ResultCandidate.summary.outcome` `succeeded` requires `errorCode: null`, and `failed` requires a non-null code (`outcome_mismatch`). A worker that reaches reporting always uploads a processing-result manifest, including on failure: check records carry the evidence, and `clips`/`outputs` may be empty. Failures before reporting are observed from executor terminal state. `ClaimGrant.startDeadline <= executionDeadline`, and each output file belongs to at most one clip.
- **Capture bridge.** Commands carry a `commandId`; an exact replay returns existing state, and changed content under the same `commandId` is `command_conflict`. Take commands return `native.capture-snapshot.v1`; failures return `native.capture-error.v1` (stable `code`, `retryable`, user-safe `message`). The snapshot is also the event payload, ordered by the persisted decimal `eventSequence`; missed events are recovered with `get_capture_snapshot`/`list_recoverable_captures`. Capture state is `preflight|recording|finalizing|finalized|recovery_required|quarantined`. `containerState` and `captureOutcome` stay null until known. `finalized` is `closed` with `completed|interrupted`, `recovery_required` is `unclosed` with no outcome, and `quarantined` is `failed`. Capture `Close.outcome` maps `completed→completed`, `aborted→interrupted`, `failed→failed` and `unknown→null`. A salvaged take is a new derived capture identity, never a success outcome of the original. Frame counters mirror `Close.frames`: submitted ≤ acquired, written ≤ submitted, and written + dropped + unresolved ≤ acquired (`progress_mismatch`). A `finalized` snapshot must also be reconciled: `videoFramesUnresolved` is 0 and written + dropped = acquired (`progress_mismatch`); a take with unresolved or missing terminal evidence is not finalized as a clean shorter take and stays `recovery_required` or `quarantined`, which may keep incomplete counters.

## Validation order and error codes

`validateBytes` / `validate_bytes` / `ContractRegistry.validateBytes` apply these steps in order and return the first failing code:

1. `document_too_large`: more bytes than the contract's `maxBytes` (1 MiB for control documents, 16 MiB for frame-map and hand shards).
2. `malformed_json`: a UTF-8 BOM, invalid UTF-8, invalid JSON (including `NaN`/`Infinity` literals and trailing data), non-finite numbers such as `1e400`, lone surrogates, or nesting deeper than 32.
3. `unsupported_version`: the discriminator (`schemaVersion` or `schema`) is present but not in the accepted set. Matching is JSON-typed, so `"1"` is not `1`.
4. `schema_violation`: JSON Schema errors, each reported with its instance JSON pointer.
5. Cross-field rules, applied in a fixed order (`src/rules.ts`, `rules.py`, `rules.dart`): `duplicate_identity`, `part_plan_mismatch` (`partCount ≠ ceil(sizeBytes / 64 MiB)`), `progress_mismatch`, `inventory_incomplete`, `reference_mismatch`, `ordering_violation`, `clock_mismatch`, `dimension_mismatch` (frame counts, crop bounds, NPZ shapes `[F,2,21,2]` / `[F,2,21]` / `[F,2,21,3]` / `[F,2]` / `[F]`), `mask_mismatch` and `outcome_mismatch` (result-candidate outcome versus error code, capture state versus container/outcome, capability outcome versus profile/reasons).

The role-conditional size bound (a `source_manifest` file is at most 1 MiB) uses `if`/`then`. Adapters report a failing conditional at different depths: Ajv reports the object and the property, Python reports the property and Dart reports the object. Those fixtures therefore pin the `schema_violation` code but no error path.

HTTP mapping for the error envelope: `unauthenticated` 401, `forbidden` 403, `not_found` 404 (absent or inaccessible), `conflict`/`idempotency_conflict` 409, `payload_too_large` 413, `invalid_request`/`unsupported_version` 422, `rate_limited` 429, `provider_unavailable` 503, `internal` 500. Error messages never include credentials, URLs with signatures or raw provider errors.

## Digests

Request hashing and manifest hashing are different operations.

**Idempotency request digest (`sa-cjson-v1`).** Creation routes store `requestSha256` with the scope `(actor, operation, idempotency key)`. An exact replay, even with different whitespace or key order, returns the original object. Changed content returns 409 `idempotency_conflict`. The digest is the lowercase hex SHA-256 of these UTF-8 bytes:

- Value domain: `null`, `true`, `false`, integers in ±9007199254740991, well-formed strings, arrays and objects. Any other number is rejected with `noncanonical_value` and is never rounded. Integral spellings such as `1.0`, `1e3` and `-0` are the same value as `1`, `1000` and `0`, because JavaScript cannot distinguish them. Invalid JSON is `malformed_json`.
- Integers are printed in shortest decimal form, without a sign on zero.
- Strings use `\"`, `\\`, `\b`, `\f`, `\n`, `\r` and `\t`. Other code points below U+0020 become `\u00xx` with lowercase hex. Everything else, including `/`, U+007F, U+2028 and non-BMP characters, is written as literal UTF-8.
- Object keys are sorted ascending by UTF-16 code units. Output has no whitespace, and array order is preserved.

This is a project-defined encoding. For this restricted value domain it is intended to produce the same bytes as RFC 8785, but no RFC 8785 conformance is claimed. The golden cases in `conformance/fixtures/digests.v1.json` were written by hand. Their digests are plain SHA-256 values of the literal canonical text, and they cover UTF-16 key ordering, escapes, non-ASCII text, safe-integer extremes and every rejection class.

**Source manifest chain.** `digests.v1.json` proves the chain with `sha256From` cases. The stored `recording-source.v1.json` bytes match the seal's `source_manifest` entry, `TaskInput.sourceManifestSha256`, `ClaimGrant.digests.sourceManifestSha256`, the grant's `source_manifest` input and `ProcessingResult.source_manifest_sha256`, which are stored under `conformance/fixtures/chain/` and `artifacts/`. A compact re-serialization of the same declaration and another sealed file's digest are `digest_mismatch`. `sealedInventory` cases cover a matching seal, order independence, missing, extra and substituted files, and role, size, digest and requiredness mismatches.

**Stored manifests.** Durable documents are hashed over their exact stored bytes (`verifyStoredBytes`). The digest lives outside the document, for example `ResultCandidate.manifestSha256`. A document never embeds its own digest, and the result manifest may not list a `result_manifest` output. Re-serializing the same value changes the digest, and a fixture proves this.

## Versioning and compatibility policy

- Every published schema file is immutable. `api/schemas.lock.json` records the SHA-256 of every file, and the policy test fails on any byte change. A breaking or additive change adds a new `*.v2.schema.json` and catalog entry. The v1 entry is never edited. A new contract adds a new catalog file (`catalog.vN.json`, an exact superset of the previous one) and appends its hashes to the lock. The policy test pins every SA-12 lock value, so existing entries can never be re-blessed.
- Readers accept an explicit set of versions per contract and reject everything else with `unsupported_version`. They never silently ignore unknown fields: unknown fields fail with `schema_violation`.
- Rollout order for a new version: (1) publish vN alongside v(N−1); (2) deploy readers that accept both; (3) switch producers to vN; (4) retire v(N−1) only after no stored or in-flight document uses it. Durable artifacts stay readable for as long as they are retained, so artifact versions are only ever added.
- HTTP versions are route prefixes. A new `/api/v2` route group may coexist with v1, and v1 bodies keep their exact shapes.
- Compatibility examples are in the fixtures: `jobs.task-input.v1` rejects `schemaVersion: 2`, `jobs.worker-claim.v1` rejects the string `"1"`, `artifacts.recording-source.v1` rejects `stateaction.recording_source.v2`, and `artifacts.hand-observations.v1` rejects `…v0`. All of these return `unsupported_version` before schema validation.

## Fixtures and checks

`conformance/fixtures/` holds the shared positive and negative cases. Every case states its expected code and the error paths that must be reported. `conformance/generate_fixtures.py` authors them deterministically, and the Python tests run it with `--check`. The fixture files are excluded from Prettier because their digests cover exact bytes.

```sh
pnpm exec nx run-many -p contracts,contracts-python,contracts-dart -t build,typecheck,test,format
```

The contracts-dart project needs the pinned Dart 3.12.2 (from Flutter 3.44.6), and its runner fails closed on any other SDK. In CI it runs in the Flutter job, and the TypeScript and Python projects run in the server and tooling job. No adapter falls back to a weaker check: an unknown contract, unresolvable `$ref`, unknown rule or unpinned SDK is an error.
