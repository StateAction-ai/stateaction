# Modal executor spike

**The public-only R3.4 E2 path fails.** The follow-up recovered the required checks with a pinned control-plane stub. See [the binding comparison](BINDING.md). The public Python SDK can invoke a pinned function and adopt and poll a call. Its deployment summaries omit fields the current TypeScript verifier needs to enforce the billing envelope and detect drift. Its call graph is best-effort and does not expose the control-plane container ID used by the GPU watchdog. The comparison covers the Python `modal==1.6.4` wheel released 2026-11-12, the JavaScript `modal@0.11.1` package released 2026-10-16, and the repository at `f5ebeb7a`. Modal documentation was checked on 2026-11-25. [Python release](https://pypi.org/project/modal/1.6.4/#files), [JavaScript release artifact](https://registry.npmjs.org/modal/-/modal-0.11.1.tgz), [Modal SDK guide](https://modal.com/docs/guide/sdk-javascript-go).

The existing [CPU protobuf fixture](../../../apps/jobs/test/fixtures/modal-deployment-wire.json) carries a request of 26,214 MiB, a limit of 8,192 MiB and a ranked startup timeout of 120 seconds. The 1.6.4 public projection reports 8,192 MiB and zero startup timeout. In the same fixture, the default and explicitly defined `min_containers = 0` override produce identical autoscaler summaries. TypeScript uses the higher memory number and rejects the defined override. The [offline test](test_modal_executor.py) reproduces the projection with the pinned wheel and the original fixture bytes.

The adapter is 154 lines, compared with 641 across the two TypeScript files, excluding the 115-line volume helper. The difference reflects the missing verification and GPU-watchdog behavior. Matching the current controller would still require raw control-plane reads or a different verified deployment contract.

## Controller interface

Import `providers.modal_executor` with `spikes/python-plane` on the import path. The separate local controller fixture uses its synchronous subprocess executor. The Modal adapter exposes async transport operations that a caller can exercise with an injected fake SDK and fake client.

- `ModalExecutor(target, *, sdk, client, api_timeout=5.0)` uses the caller's SDK and explicitly supplied client. The caller owns the client's lifetime. `ModalTarget` carries `app_name`, `function_name`, `environment_name`, `function_id` and optional `version`.
- `spawn(bootstrap, can_submit)` returns the provider call ID after one SDK invocation. The caller's synchronous authorization check must cover the current lease and independent deployment verification. `ModalSpawnNotSent` means the SDK spawn method was never invoked. `ModalSpawnUncertain` means it was invoked and the outcome could not be established. If cancellation interrupts an issued spawn, the caller keeps the journal intent.
- `poll(call_id)` returns `returned` with a value, or `pending` or `unavailable` with a detail code. The caller validates returned values before recording terminal state.
- `cancel(call_id)` requests cancellation with container termination. `inspect()` and `watch(call_id)` expose diagnostic summaries and lineage.

The tests exercise lookup, result observation and failure handling with fakes and decode a recorded fixture offline. Version retention, SDK retry deduplication, deployed execution and physical cancellation remain unverified. [Locked test commands](../contracts/README.md).
