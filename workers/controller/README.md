# Python pipeline controller

The Render entry point is `python -m stateaction_controller.workflow`. It registers `process-recording` using the existing `{jobId}` input and the actual Render task run ID. The controller uses the existing internal jobs routes for leases, claims, stage settlement and execution evidence.

A controller entry requires an explicit `EXECUTION_BACKEND`, `APP_ENV`, API origin, controller capability, and a private `JOBS_STATE_DIR`. Local runs use the processing environment's Python executable. The worker receives a one-time bootstrap through stdin. Modal runs use the controller's own SDK client and the same module target settings as the TypeScript controller. Before starting a GPU call, the controller requires a verified definition with a bounded rate, container count and billed duration. A configured GPU target without that proof returns `needs_operator` before it issues a claim. Verified definitions use the digest emitted by the pinned Python verifier. Issuing those bindings and switching the hosted task are separate release steps. Both controllers verify the definition and then submit by function ID. A redeploy in that interval can change the definition while preserving the ID.

Each journal records an immutable start and execution deadline and the exact child or provider call identity when known. The controller persists a single-use spawn reservation before dispatch. A lost acknowledgement leaves the reservation intact. Recovery can adopt an observed execution by its exact identity. A retry of the recorded run can publish exact evidence after the job ends. This path only observes and reports evidence. A cancellation request alone never records terminal evidence. An intent already recorded by the API can dispatch once while cancellation is pending. The controller then supervises that exact execution and requires terminal proof. Temporary one-time bootstrap files use owner-only permissions and are removed on handoff or when recovery establishes that submission is fenced.

Run `uv sync --locked` in this directory and `uv run --locked pytest -q tests` for focused checks. Local integration uses the existing bounded Postgres and storage fixtures, the production Next build, the pinned Render CLI and the real processing fixture. Run it through the repository's `controller-python:integration` Nx target. It exercises control flow and evidence with synthetic inputs.

The existing TypeScript operator commands serve the running TypeScript controller. The Python helpers read the Python controller's journals, including spawn binding provenance.
